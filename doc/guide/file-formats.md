# File Formats

## Which mode opens what

| Extension | Mode | Notes |
| --- | --- | --- |
| `.step` `.stp` `.iges` `.igs` `.brep` | 🔷 Pre-Processing | B-rep, tessellated by OpenCascade |
| `.csg` `.scad` | 🔷 Pre-Processing | OpenSCAD. `.csg` (the fully evaluated form) is parsed and built kernel-side into a solid; `.scad` is converted to `.csg` first by a **user-installed `openscad` binary** (**Settings ▸ Open Settings… ▸ CAD Viewer ▸ OpenSCAD Binary**, or `openscad` on `PATH`) — without one, opening a `.scad` reports that rather than failing silently. Import-only: export goes to STEP/IGES/BREP or a mesh target, never back. Anything the importer approximates or skips (a `hull()`, a faceted cylinder) is reported on the status line |
| `.gltf` `.glb` | 🔷 Pre-Processing | Loaded natively by Three.js |
| `.3mf` `.dae` | 🔷 Pre-Processing | 3MF and Collada, loaded by Three.js in the viewer. **Display-only**: they open, show, and (for 3MF) export, but the host has no triangle parser for either, so meshing, measurement, region fitting, Mesh Health, silhouette/drawing-sheet exports and B-rep promotion are refused by name — export to STL, OBJ, PLY or glTF first. Collada is import-only: there is no Collada writer |
| `.mdpa` | 🔶 Post-Processing | Kratos model part |
| `.vtk` `.vtu` `.vtp` `.vti` `.vts` `.vtr` `.vtm` | 🔶 Post-Processing | Legacy + XML VTK, multiblock, time-series |
| `.msh` `.inp` `.bdf` `.nas` `.fem` `.unv` `.mesh` `.vol` `.su2` `.xdmf` `.xmf` `.off` `.avs` `.dat` `.tec` `.mphtxt` `.node` `.ele` `.f3grid` `.pf3` `.post` `.dato` `.ugrid` `.mfm` `.wkt` `.xml` `.dex` `.ip` `.mff` `.case` `.geo` `.poly` `.e` `.exo` `.ex2` `.cgns` `.h5m` `.hmf` `.med` `.foam` | 🔶 Post-Processing | Extended formats read via [meshio++](https://github.com/nschloe/meshio) (Gmsh, Abaqus/ANSYS, Nastran, I-deas UNV, Medit, Netgen, SU2, XDMF, COMSOL, tetgen, EnSight Gold, Triangle, Exodus II, CGNS, MOAB, Salome MED, OpenFOAM, …). Named groups (Gmsh physical groups, Abaqus `*NSET`/`*ELSET`/`*SURFACE`, Exodus element blocks / node sets / side sets, OpenFOAM boundary patches) arrive as SubModelParts. `.e`/`.exo`/`.ex2` (Exodus) and `.xdmf`/`.xmf` describe their time steps within the dataset and drive the timeline from there (XDMF may reference a required sibling `.h5`; copy it too) — no `<prefix>_<rank>_<step>` sibling naming needed; Salome `.med` also accepts a time step, but reports no step count up front, so its timeline isn't discoverable before a read. `.dex`/`.ip`/`.mff` are field-only formats — they carry point fields with no geometry, so reading one yields a point cloud (or an empty mesh); `.case`/`.geo` (EnSight Gold) and `.poly` (Triangle) need their sibling file(s) alongside. `.foam` is an OpenFOAM case: the file you open is a 0-byte marker, and the real mesh — volume cells as Elements, boundary faces as Conditions, one named SubModelPart per boundary patch — lives in a sibling `constant/polyMesh/` tree, which the preview also watches, so re-running `blockMesh`/`snappyHexMesh` refreshes the view in place. The time directories (`0`, `0.5`, …) drive the timeline: their fields arrive as **Elemental** (`vol*Field`) or **Nodal** (`point*Field`) fields, and a patch carrying one uniform `boundaryField` value arrives as a **Conditional** field of the same variable, with the file's `dimensions` kept as its unit. Zones (`cellZones`, `faceZones`, `pointZones`) become SubModelParts; a **multi-region** case (one `constant/<region>/polyMesh` each) opens with every region merged and each region a top-level SubModelPart, and a **decomposed** case (`processorN/constant/polyMesh` plus the `*ProcAddressing` files) is reconstructed into one mesh with processor0's patch names — run `reconstructPar` first if you need its fields. Not read: `#include`/coded/substituted field content, binary fields, nonuniform patch values. **File ▸ Save writes back into the case**, and only the files it can own: a geometry- or field-only change rewrites just `constant/polyMesh/points` (plus the `internalField` of an edited field), so nothing keyed by cell/face/point number can go stale; a topology change rewrites the six polyMesh files and then **refuses by file name** if anything else is keyed to the old numbering (`faceZones`, `pointZones`, `sets/`, `cellLevel`, `pointLevel`, `refinementHistory`, `surfaceIndex`, a moving-mesh `<time>/polyMesh`, a time-directory field holding a `nonuniform` list), as it does for polyhedral cells; a multi-region or decomposed case saves in place for coordinate-only edits, with any change to cells or patches refused. Exporting *into* the case (another `.foam` name, a sub-part, a derived or batch output) is refused — use **Export ▸ Solvers ▸ OpenFOAM** or **Save As…** to write a new case directory instead |
| `.fil` `.rst` `.rth` `.d3plot` `.t19` `.op2` `.xplt` `.h5` | 🔶 Post-Processing | Solver-result formats, also read via meshio++: Abaqus `.fil`, ANSYS MAPDL `.rst`/`.rth`, LS-DYNA `.d3plot`, MSC Marc `.t19`, MSC Nastran `.op2`/`.h5` and FEBio `.xplt`. All read-only, and none of them reports its steps from a header — so each opens as a **filename series** (a single frame, no timeline scrubber), the same bar CalculiX `.frd` sits behind. Four more upstream readers exist but are reachable by an explicit format only, because upstream finds them by file *name* rather than by extension: a cyclic model's full rotor, LS-DYNA `binout`, and the two Radioss animation forms |
| `.stl` `.obj` `.ply` | Both | Opens in the **currently active** mode |

The meshio++ 16.41 reader set also covers Code_Aster (`.mail`), FEBio (`.feb`), Femap (`.neu`), libMesh (`.xda`/`.xdr`, including `.gz` and `.bz2`), COMSOL binary (`.mphbin`), Patran (`.pat`/`.out`), Radioss (`.rad`), Z88 (`.z88`), Elmer (`.elmer`) and MFEM partition files (`.mfem-rank`). GiD postprocess, PVD collections, XDMF, MED, CGNS, Tecplot, VTKHDF and OpenFOAM cases can expose in-file timelines; see [Post-Processing](/guide/mesh-mode#timeline-discovery) for the live-watch and resampling behavior.

Pre-Processing can *also* read `.vtk` `.vtu` `.med` `.cgns` `.exo` `.e` `.xdmf` `.mdpa` `.msh` `.inp` `.unv` `.su2` `.mesh` `.post.msh` `.foam` through meshio++, as a **geometry-only boundary surface** (named regions become Parts; fields are not converted, though a scalar point/cell field can be used to colour the model). Those are post-processing formats here and mesh mode reads them natively — fields, blocks and SubModelParts — so opening one always lands in Post-Processing regardless of the active mode. Reach the CAD-side importer from Pre-Processing's own **Open…** dialog (or drag the file onto the CAD view) when you specifically want to mesh or edit that geometry.

`.msh2` (Gmsh 2.2) goes the other way and opens in **Pre-Processing** whatever the active mode — the mesh engine never registered it at all, so cad mode is the only one that can open it.

## If a file won't open

Opening a file no mode can read — from **Open…**, a drag-and-drop, a recent entry, or a launch from the operating system or command line — shows a warning naming the file and the suffix KKSS does not read (`.post.msh` is reported as a compound suffix, never as `.msh`), with a **Supported formats** button that opens this page. A file with no extension is reported as such, since its format cannot be told from the name. When several unsupported files arrive at once, one warning names the first and counts the rest. Every format either mode reads is already routed to the mode that owns it (see the table above), so a message never means "try the other mode".

## Export targets

**Pre-Processing** (depends on the source pipeline):

- B-rep sources → STEP, IGES, BREP, STL, OBJ, PLY, glTF
- Mesh sources → STL, OBJ, PLY, glTF, 3MF (no mesh→B-rep path exists)
- FE meshing → Kratos MDPA (Elements+Conditions or Geometries), Gmsh `.msh` / `.msh2` / `.geo_unrolled` (+ XAO companion), VTK, UNV, Abaqus `.inp`, Nastran `.bdf`, SU2, and more — plus MED, CGNS and XDMF (+ its `.h5` companion) written through meshio++, which Gmsh's own writers can't produce
- Screenshot → PNG (**File ▸ Screenshot…**, `Ctrl+Alt+P`)

Every export target can optionally be **unit-converted** (mm/cm/m/in/ft) on the way out: a second quick-pick after the format, defaulting to native mm. This is a real geometric scale on the exported file — STEP and IGES also get their declared header unit written to match — not the display-unit selector in the view controls, which only changes how measurements read. A CGNS export of a pure surface mesh is a known gap: it writes, but meshio++'s own reader can't read it back (volume meshes are fine).

When an FE-meshing export produces a file Post-Processing can display (`.mdpa`, `.vtk`, …), the app switches to Post-Processing mode and opens it automatically — a one-way pre → post handoff. Exports the post viewer can't open (`.msh`, `.inp`, …) and shared formats (`.stl`/`.obj`/`.ply`) stay in Pre-Processing.

**Post-Processing**: MDPA, VTK (legacy), VTU, VTP, VTM, STL, OBJ, PLY — for the whole model or any single SubModelPart, or just the **boundary skin** of the volume cells (**Advanced ▸ Export skin…**) — plus 49 extended writable formats via [meshio++](https://github.com/nschloe/meshio) (Gmsh `.msh`, Abaqus `.inp`, Nastran `.bdf`/`.nas`/`.fem`, I-deas UNV, Medit `.mesh`, Netgen `.vol`, SU2, XDMF, Triangle `.poly`, Exodus `.e`/`.exo`/`.ex2`, CGNS, MOAB `.h5m`, `.hmf`, Salome `.med`, and more), including the field-only `.dex`/`.ip`/`.mff` targets (point fields kept, geometry dropped) and the write-only SVG/TikZ figure formats (a 2D/3D-projected drawing of the mesh, not a re-readable mesh). **File ▸ Export Mesh As** groups these targets; **Export…** retains the picker and shortcut.

SubModelParts survive an export to `.mdpa`, `.med` (as MED families) and `.inp` (as real `*NSET`/`*ELSET` sets), and every mesh block keeps its name in `.exo`; a `.msh` export still carries no groups (meshio++ writes no `$PhysicalNames` for a mesh that didn't come from Gmsh). Exodus export remains lossy — element blocks and fields survive, genuine SubModelParts do not, and a time series flattens to one step. Native VTU does not retain SubModelPart sets: use MDPA or MED when those memberships matter, and inspect the fidelity report. VTM writes a multiblock index plus VTU companions. Structured VTK types (`.vti`/`.vts`/`.vtr`) are not general mesh-export targets; structured VTI has its own sample-grid export path with explicit unverified fidelity.

### How format counts are measured

The routing registries currently expose **61 extended readable formats** and **49 extended writable formats** through meshio++. These count distinct format identifiers, not suffix aliases: Exodus `.e`/`.exo`/`.ex2` count once, while alternative readers for a shared suffix count separately. Native formats are separate. The counts include field-only `.dex`/`.ip`/`.mff` formats; the writable count also includes SVG and TikZ figures, which cannot be read back as meshes. `npm run check:packaging` derives both counts from the pinned registries and rejects mismatched documentation.
