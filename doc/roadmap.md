# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two upstream VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* behind a fake `vscode` module — with scoped workflow-contract changes committed on their integration branches, OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over three MCP servers whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running — and whose image results are shown in the sidebar, a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** A change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for MCP contracts, `application-downstream` for extension code), is committed there, and is integrated here through its gitlink — never as an uncommitted patch or on the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

## Queued

### Tier 0 — Defects and doc drift

*Admission: shipped behavior that strands a user or loses work, or documentation that contradicts the shipped app. Always top priority regardless of effort.*

1. **Home's study actions are built on `window.prompt`/`window.confirm`** (**M**). `app/renderer/home/home.ts` asks for sweep parameters and values, the quantity's field, component, region, reduction and unit, and whether to reuse a mesh through 26 native `prompt()`/`confirm()` calls. Electron does not implement `window.prompt()`, so every flow gated on one — **Plan sweep** and **Evaluate quantity** at least — most likely does nothing; and no e2e scenario under `tools/` or `test/` clicks these buttons, which is how it went unnoticed. Confirm first with an Electron acceptance case, then replace the prompts with an in-page form built from `kkss-ui.css`'s `.field`/`.seg`/`.btn` recipes (no inline `style=`, the page's CSP forbids it), with explicit validation messages instead of silent early returns. The same form is the natural home for items 5 and 9's inputs. *Chat parity: none* — the `app__*` workflow tools the buttons call are already the assistant's route and are unaffected. *Docs:* `getting-started.md`'s guided-simulation section and a regenerated Home screenshot.

2. **Ctrl+O replaces a mesh tab's document without the dirty-state prompt** (**S**). Closing a dirty mesh tab and quitting with one both go through `index.ts`'s `confirmDiscardMeshTab` (Save / Don't Save / Cancel), but opening a file *over* that tab does not — `CLAUDE.md` records it as "not yet extended to this path". It is the one remaining way to lose applied-but-unsaved mesh operations with a single keystroke. Route every replace-in-place open (menu, toolbar button, drag-and-drop, home recents) through the same guard; launch-time and second-instance opens already take a new tab and need nothing. *Chat parity: none* (the assistant's `mesh__*` tools do not replace tab documents). *Docs:* `getting-started.md`'s tab section and shortcut table.

3. **One source for the supported-format counts** (**S**). `doc/index.md` advertises "44 extended mesh formats" while `doc/guide/file-formats.md` says "~36 extended formats", and neither says whether it counts readable or writable formats. `npm run check:packaging` already parses both submodules' routing registries; emit the read and write counts from the same parse and have the docs quote them (or a build check fail on a mismatch), so a submodule bump cannot silently desynchronize the numbers again. *Chat parity: none* (docs/tooling).

### Tier 1 — Submodules stay current

*Admission: keeping `cad/` and `mesh/` at their latest release, with the features they gain actually reachable from the app.*

4. **Gitlink currency, with the mirror checklist a bump actually requires** (**S** per bump, recurring). Both submodules must track their latest release and the new features must be *integrated*, not merely present in the tree — a bump that builds is not a bump that works. The full checklist lives in `doc/guide/development.md` under **Submodule release maintenance**: review the upstream notes and diff on the right branches (`kkss.dev` for MCP changes, `application-downstream` for extension code); run `npm run package --prefix mesh` before the parent build and confirm `out/meshio/dist/meshioplusplus_wasm*` lists all four files; mirror `tools/webviewMarkup.ts`'s mesh body element for element against `buildPreviewHtml`; extend `vscodeShim.ts` rather than patching, and give menubar-only actions native menu routes; classify new MCP tools in `toolPolicy.ts`; build the CAD MCP kernel via `cadMcpWorkerConfig`, never copy upstream's artifact; then typecheck, test, smoke, docs and screenshots. *Chat parity:* a new viewer or file capability is only useful to the assistant if the submodule's own MCP server exposes it — if it doesn't, that is upstream work on the submodule's `kkss.dev` branch, and the gitlink bump waits for it. A new **app-level** ability arriving with the bump needs the system-prompt description updated in the same change.

### Tier 2 — Guided workflow completeness

*Admission: closes a documented limit of the shipped study → queue → review → compare stack in `app/main/services/workflows/`. Every item keeps the existing rules: persist intent before starting work, never infer convergence from process exit, preserve missing values as null.* *Chat parity for the whole tier:* these change what the `app__*` workflow tools return or accept, so each item updates their schemas and descriptions in `service.ts` and the system prompt's workflow paragraph in `chatService.ts`, and a new tool needs its `toolPolicy.ts` row.

5. **Apply the thread suggestion to solves** (**S**). `environment.ts` computes `suggestedThreads` (only when the manual runner exposes verified thread control) and Home displays it, but nothing in `queue.ts`/`service.ts` passes it to the solve — so queued runs use whatever the solver defaults to, and the suggestion is capped at 4 regardless of core count. Add a `kratos.threads` registry setting (default: the suggestion), apply it through the runner's verified thread control, record the value used in the run's provenance so a comparison can see it, and revisit the cap with a measured rationale. *Docs:* `getting-started.md` and `configuration.md`.

6. **Convergence evidence beyond the structural problemtype** (**M**, *needs upstream submodule work*). `review.ts` answers "unavailable" for every run whose `problemtypeId` is not `structural`, because only that problemtype's generated case writes the versioned `kkss-convergence` monitor. The fluid, thermal, potential-flow and shallow-water tutorial cases already have verified solver baselines (`tools/tutorials/`), which makes them the right first targets and their acceptance data. Needs each mesh problemtype's case generator to emit the monitor (mesh `kkss.dev`) plus a per-problemtype adapter id here; criteria a solver does not publish stay unavailable, never estimated.

7. **Mesh statistics for non-MDPA meshes** (**S**). A review of a run whose mesh is not `.mdpa` reports "Mesh statistics are unavailable for this format" (`review.ts`'s `mdpaCounts` is a text parser). The mesh MCP server already reads every routed format; call its read-only statistics path for other formats, keeping the MDPA fast path.

8. **Result discovery beyond `vtk_output/`** (**M**). The solve task's required artifact and result discovery are hard-wired to `vtk_output` (`service.ts`), so a case configured for XDMF/HDF5 or GiD post output completes with its results invisible to review and quantity evaluation — even though mesh mode reads those formats. Discover outputs from the generated case's output-process settings instead of a fixed directory name.

9. **Mesh-sensitivity numbers, not just the label** (**M**). `comparison.ts` already classifies a variant set as a mesh-sensitivity study from recorded mesh revisions. When three or more such variants share one quantity definition, add the observed order, Richardson-extrapolated value and grid convergence index, with the refinement ratios and the assumptions (asymptotic range, monotone convergence) printed beside the numbers and the result withheld when they fail — the heuristics-must-stay-visible rule from the Magnusim review.

10. **Readable review and comparison reports** (**S**). The offline HTML exports are one convergence plot plus the raw JSON (`review.ts`, `comparison.ts`). Render findings, provenance, mesh statistics/quality and the saved quantities as tables, keeping the JSON as the machine-readable twin. Still one self-contained file with no network fetches.

11. **Independent light tasks alongside a solve** (**M**). `queue.ts` has one global execution slot, so meshing the next variant waits for an unrelated solve to finish. Add a separate slot for mesh/case-generation tasks whose dependencies are satisfied, keeping the solve slot single and the dispatch-intent persistence unchanged; a resource cap (item 5's thread count) decides whether both may run at once.

12. **An MPI runner contract** (**L**). `EnvironmentReport.mpi` is the literal type `false`, and the UI rightly hides rank controls because there is no verified way to launch, observe and reconcile a distributed Kratos run. The contract needs: probing a working `mpirun` and Kratos's MPI build, a launch receipt the queue can reconcile after a restart, partitioning of the generated case, and a reconcile path for a partially-dead rank set. Only then may `mpi` become a boolean.

*Admission: `app/main/cadHost.ts` is a 1:1 port of `cad/src/provider.ts`; a message or flow the provider has and the port lacks is a gap here, not a KKSS design choice. Deliberately-not-ported features (SpaceMouse, the Models view, `zoomToSelection`) stay excluded.*

13. **Complete the `geometry` post** (**M**). `handleBRep` sends only meshes/edges/points, while the provider also sends `autoFit`, `opOutcomes` (rebased by `bakedThrough`), `guideIds` and `opBuckets` — so in KKSS the Edits panel never flags an op the kernel skipped, and `guide: true` construction geometry is drawn like real geometry. 14. **Interactive bake — Save into the source file** (**M**). KKSS never advances `bakedThrough`, so an edited STEP/IGES/BREP/STL/OBJ/PLY shows "N unsaved edits" permanently (`doc/guide/cad-mode.md` explains it rather than fixing it). 15. **Say what *can* open when a format cannot** (**S**). An unroutable file only produces a generic toast (`index.ts`, `cadHost.ts`). Name the detected suffix, link the supported-formats page, and when the file is a known-but-other-mode format say which mode opens it. *Chat parity: none.*

### Tier 4 — Assistant and MCP

*Admission: tightens or clarifies what the assistant and the external MCP endpoint may do, or removes a prompt that carries no information. Each item is itself chat-facing, so its chat-parity cost is the item.*

16. **An approval policy for the HTTP meta server** (**M**). `metaServer/buildServer.ts`'s `callToolRaw` is deliberately un-gated — bearer token only — so any client holding the token can run every write-class tool, including solver runs. Add a **Settings ▸ MCP Server ▸ Allowed tools** choice (read-only / read + listed writes / everything, default read-only for newly enabled servers, existing configurations keep "everything"), classified with the same `toolPolicy.ts` table; a refused call returns a clear MCP error rather than a silent no-op. *Docs:* `development.md`'s meta-server section, `configuration.md`.

17. **Path-scoped write approval** (**M**). Approval is per tool name only; "Always allow in this conversation" allows a write tool anywhere. Add "Always allow writes inside the project folder", keyed on `projectRoot.explicit()` (never the inferred root) and a per-tool declaration of which argument names are paths, falling back to asking when a tool's paths cannot be determined. The HTTP server can reuse the same scope for item 16.

18. **Classify the pinned Kratos server's tools** (**S**). Every `kratos__*` call asks for approval because `toolPolicy.ts` has no rows for them, which turns the gate into noise for read-only calls like `job_list`/`job_status` (the Jobs panel already keeps its own read allow-list). Add reviewed rows pinned to `KRATOS_MCP_VERSION`, with a test that fails when the pin moves without the table being re-checked — the same discipline the cad/mesh key set already has.

19. **User-entered prices for unlisted models** (**S**). An OpenAI-compatible gateway resolves to no `modelInfo.ts` row, so the sidebar shows tokens with no cost or context percentage. ### Tier 5 — Robustness

*Admission: a failure mode the app currently only logs or documents, where a bounded, user-initiated recovery exists.*

20. **A "renderer not responding" prompt** (**S**). `unresponsive` is only logged (`windows.ts`) — deliberately never wired to automatic reload, since a large mesh parse trips it. Offer a *user* choice (Wait / Reload this tab) only after the renderer stays unresponsive past a generous threshold, reusing the existing crash-recovery replay; never reload without the click. *Chat parity: none* (window chrome).

21. **Cloud write-back for nested export trees** (**M**). The staging watcher runs at `depth: 0`, so an OpenFOAM export's `constant/polyMesh/` tree (and anything else nested) is never uploaded. Watch known companion directories per format, upload them with the same revision/conflict rules, and keep the one-document-per-directory invariant. *Chat parity: none* (sync is below the tool layer). *Docs:* `getting-started.md`'s cloud section.

22. **Re-download evicted cloud documents on session restore** (**S**). Restore is synchronous and never stats, so an evicted cloud file lands in the "could not be found" toast even though its recent entry could re-download it. After restore, fetch evicted cloud documents in the background and open them into their saved tabs, without making restore itself asynchronous.

### Tier 6 — Remote sessions

*Admission: lets the app reach a machine other than the one it runs on, without breaking the invariant that everything below the staging layer sees ordinary local files.*

23. **Connect to a remote host over SSH** (**L**). Pre-process on a laptop, but open meshes and results that live on a workstation or cluster login node, and run Kratos there, from the same window. The shape follows two things the app already does, so the rest of the app stays unaware of the remote:
    - **Files** are staged exactly like cloud documents (`services/cloud/`): download into `<userData>/remote-cache/<host>/<opaque-id>/<original filename>`, hand *that* path to `openFile()`, and write back from the staging watcher with a remote-mtime/size conflict check and a side-by-side conflict copy. Routing, `allowRoot()`, both hosts and the submodules' MCP servers need no change. A **File ▸ Open Remote…** browser lists the remote directory; recents carry a `remote` ref like the cloud ones.
    - **Terminal, runs and the Kratos MCP server** go through the **system `ssh` binary** (OpenSSH ships on Windows 10+, macOS and Linux): the terminal panel spawns `ssh -t <host>` through the existing node-pty; `McpManager` can spawn the Kratos server as `ssh <host> uvx … kratos-mcp-server@<pin>` over the same `StdioClientTransport`, so the assistant's solver tools and the Jobs panel run on the remote with no protocol change; the queue's solve runner launches and reconciles remotely through a receipt in the remote run directory.
    - Using the system client keeps the user's `~/.ssh/config`, agent, keys, `ProxyJump` and known-hosts handling authoritative, and adds **no dependency** — a JS SSH library would bring its own key handling and an optional native crypto module, which the "second native module" Non-goal rules out. KKSS never stores a password or passphrase; connection reuse is ssh's own `ControlMaster` where the platform supports it.
    - Out of scope for the first cut: port-forwarding a remote KKSS UI, and running the WASM kernels remotely (OCCT, Gmsh, MMG and meshio++ stay local, on staged bytes).

    *Chat parity:* the context suffix names the active remote host and the staged-versus-remote path of each open document (`ChatDeps.currentFiles()`); the system prompt learns that Kratos tools may run remotely; a remote host list lives in a settings-registry entry. *Docs:* a new `doc/guide/remote-sessions.md`, `getting-started.md`, `development.md`'s architecture section, and a `CLAUDE.md` invariant for the remote staging layer.

## Non-goals / known constraints

- **Keeping app-specific submodule patches uncommitted or on a release branch** — shared workflow contracts can require upstream changes; commit those on the designated integration branches and move the parent gitlinks only to their committed revisions.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature.
- **A dirty-state prompt when closing a CAD tab** — until item 14 lands, cad has no app-level "unsaved changes" concept: its sidecars autosave on a debounce, so closing a CAD tab is a plain dispose. (Mesh tabs *do* prompt since mesh 3.18.0 gave its previews real dirty state; item 2 closes the one path that still skips it.)
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image is a separate tag of a separate distribution, and the installer stays lean.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image), the authenticated web front end and a reference per-user orchestrator so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 25 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **1 → 5, 9.** The thread setting and the mesh-sensitivity inputs need a working Home form; building them on `window.prompt` would repeat the defect.
- **5 → 11 → 12.** A second queue slot needs a resource cap to decide what may overlap, and an MPI contract needs both the thread control and a multi-slot queue to reason about ranks.
- **13 → 14.** Rebasing `opOutcomes` by `bakedThrough` is the load-path threading an interactive bake depends on; baking first would leave the Edits panel mislabelling ops after every save.
- **18 → 16, 17.** The meta server's allow-list and path scoping both classify through `toolPolicy.ts`; without Kratos rows every Kratos tool would be refused (16) or always prompt (17).
- **21 → 23.** Remote staging reuses the cloud layer's watcher and write-back; an export tree (a results directory, an OpenFOAM case) is the normal remote case, so nested-tree write-back must exist first.
- **8 → 23.** Remote solves only become reviewable if result discovery reads the generated case's output settings rather than a fixed local `vtk_output/`.
- **25 → 27.** The remaining sharing and resize validation must be settled before the container and hardware acceptance checks can close.
