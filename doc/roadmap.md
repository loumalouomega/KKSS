# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two upstream VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* behind a fake `vscode` module — with scoped workflow-contract changes committed on their integration branches, OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over four MCP servers (CAD, mesh, Kratos and a pinned PDF reader) whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running — and whose image results are shown in the sidebar, a composer that attaches images and PDFs (stored with the conversation, refused up front where a provider cannot take them), a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** A change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for MCP contracts, `application-downstream` for extension code), is committed there, and is integrated here through its gitlink — never as an uncommitted patch or on the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

### Tier 6 — Remote sessions

*Admission: lets the app reach a machine other than the one it runs on, without breaking the invariant that everything below the staging layer sees ordinary local files.*

15. **Connect to a remote host over SSH** (**L**). Pre-process on a laptop, but open meshes and results that live on a workstation or cluster login node, and run Kratos there, from the same window. The shape follows two things the app already does, so the rest of the app stays unaware of the remote:
    - **Files** are staged exactly like cloud documents (`services/cloud/`): download into `<userData>/remote-cache/<host>/<opaque-id>/<original filename>`, hand *that* path to `openFile()`, and write back from the staging watcher with a remote-mtime/size conflict check and a side-by-side conflict copy. ### Tier 10 — Assistant extensibility

*Admission: lets the user add their own MCP servers, standing instructions, skills and lifecycle hooks to the assistant. Nothing added this way may widen what the approval gate lets through, and anything a project folder supplies waits for the folder-trust record that item 23 introduces.*

23. **An MCP manager in the chat sidebar** (**M**). The sidebar runs three fixed servers, keyed by a closed `"cad" | "mesh" | "kratos"` union (`ChatServerStatus` in `app/main/ipc.ts`; `buildServerSpecs` in `mcpManager.ts`). It shows a status dot for each, and a retry action for Kratos alone. Add a manager panel: each server's state, tool count and last error (the status already carries these), enable, disable and restart controls, an **Add server** form for a stdio command (command, arguments, environment) or a streamable-HTTP URL with a bearer token, and each server's tool list. The user marks each tool read or write. Marks are keyed by server id and tool name, default to *unknown ⇒ ask*, and are never inferred from a tool's name or annotations, as `toolPolicy.ts` already requires. User-level servers live in the app's state store; project-level ones in `.kkss/assistant/mcp.json`, beside the workflow store's `.kkss/project.json`. Four constraints:
    - **Reserved ids.** Ids are lowercase letters, digits and hyphens only, since `splitToolName` splits at the first `__`. `cad`, `mesh`, `kratos`, `app` and `mcp` are reserved. Classification is keyed by the full name, so a user server named `cad` that exposes `list_layers` would produce `cad__list_layers`, inherit that read row and skip the prompt.
    - **One gate for every runtime.** Every chat tool call, whichever runtime makes it, passes `executeTool`. A user server must not be added to a vendor CLI's own server list: `agents/claude.ts` gives the Claude CLI exactly one server, `kkss`, and a second entry would be a tool path the gate cannot see.
    - **The meta server waits for item 7.** Its `callToolRaw` path is un-gated, so user-server tools stay out of its tool list until item 7 adds an allow-list.
    - **Folder trust.** A project's `.kkss/assistant/mcp.json` names a command that would run on the user's machine. Its first use raises a trust decision keyed on `projectRoot.explicit()`, never the inferred root, which is the rule `discoverExternal()` already follows for `.kratos/problemtypes`. The record stores a hash of the definition files, so a later pull that adds a server asks again. Items 24 and 25 list their definitions in this panel and reuse the same record.

    Environment values and bearer tokens go through `chat/secrets.ts`, and no renderer ever receives one. *Chat parity:* per-server state rides `contextSuffix()`, and the system prompt changes once, in its namespace paragraph. The server list is a settings-registry entry, so the one-registry rule holds. User tools take their marks from the manager, and `toolPolicy.ts` keeps its built-in rows. *Docs:* a new `doc/guide/assistant-extensions.md`, `configuration.md`'s **LLM assistant** section, `development.md`'s **AI chat sidebar** section. The sidebar changes, so re-run `npm run docs:screenshots`.

24. **Standing instructions, skills and prompt templates** (**M**). The assistant has one fixed `SYSTEM_PROMPT` and nowhere for the user's own standing guidance, such as a lab's unit conventions or a checklist to run before every solver launch. Settings ▸ LLM Assistant has no field for it. Add three text-only definitions. None can execute code, add a tool, or make a write skip the gate.
    - **Instructions**: `instructions.md` in `<userData>/assistant/`, plus `.kkss/assistant/instructions.md` in the explicit project folder once trusted. They ride `contextSuffix()`, not the system prompt, so the cached prefix survives. They are re-sent as uncached input on every turn, so the item caps their size and shows it in the readout.
    - **Skills**: `<name>/SKILL.md` with a name and a one-line description. The context suffix carries only a catalog of names and descriptions, and a read-class `app__skill_load` tool returns a body on demand, so an unused skill costs one catalog line.
    - **Prompt templates**: `/name` in the composer expands to stored text before the send. The transcript keeps the expanded text the model actually saw, never a reference that could change later.

    Project-folder instructions and skills change what the model is told on every turn, so they load only after folder trust (item 23). The vendor CLIs' own settings, instructions and skill discovery stay off on the subscription runtimes (`settingSources: []`, and the skill flags in `CODEX_RESTRICTIONS`), so these definitions reach those runtimes only through the same context path. *Chat parity:* this item is the chat surface. `app__skill_load` needs an `appTools.ts` entry and a read row in `toolPolicy.ts`, and the system prompt gains one sentence saying a skill catalog exists. *Docs:* `assistant-extensions.md`, `getting-started.md`'s **AI assistant** section, `configuration.md`'s **LLM assistant** section.

25. **Lifecycle hooks for tool calls and turns** (**L**). Approval is decided per tool name today, and item 8 adds path scope. Neither lets a user write a rule of their own, such as "no solver launch outside the study folder" or "append every write to our audit log", without changing KKSS. Hooks run a user's command at four points: `PreToolUse` (before approval, may deny), `PostToolUse` (after the call, observes), `UserPromptSubmit` (may refuse the message) and `TurnEnd` (observes).
    - A hook receives one JSON object on stdin: the event, conversation id, tool name, arguments and the open files from `currentFiles()`. Exit 0 is no opinion; exit 2 denies, with stderr as the reason. Any other outcome (timeout, crash, other exit code) denies a `PreToolUse` hook and is only logged for the other events.
    - A hook can deny a call or force a prompt, but it can never approve one. A hook that could approve would be the gate approving itself.
    - Each hook has a timeout (10 s by default) and capped output. It is killed on abort and in `flushSync()`, because `settleTurn()` awaits the turn, and a hook that ignores abort would hang Stop, New chat and quit.
    - A denial appends the `toolResult ok:false` the gate already requires, carrying the hook's name and reason, so the model does not retry. The decision goes on the `toolCall` entry as an optional field, following the `approval` precedent, so no `CHAT_STORE_VERSION` bump.
    - `PreToolUse` sits inside `ChatService.executeTool`, so the API loop and both subscription runtimes share it. The vendor CLIs' own hooks stay off (`features.hooks: false` in `CODEX_RESTRICTIONS`, `settingSources: []` on the Claude side), which keeps one hook system. Item 7 decides whether the meta server runs `PreToolUse`; it should, so a hook is the policy for every client.
    - Project hooks (`.kkss/assistant/hooks.json`) run only after folder trust. Hook output appears beside the tool call and reaches the model only when the hook opts in, labelled as hook output.

    *Chat parity:* a hook denial names the hook, and the system prompt gains one sentence on what that denial means. The classification tables do not change, because hooks decide per call, not per tool. *Docs:* `assistant-extensions.md`, the gate section of `development.md`, `configuration.md`'s **LLM assistant** section.

### Tier 11 — Presentation

*Admission: changes how an existing surface looks or moves. It may add a preference row, but no capability, IPC message, conversation data or model-visible context. Ranked last by design, so polish never competes with the tiers above.*

26. **Kraty, an animated chat companion** (**M**; static faces alone are **S**). An original Clippy-style character inspired by Kratos Multiphysics (not its logo or upstream artwork), drawn in TypeScript as SVG in `app/renderer/chat/` with no new dependency. Its face mirrors state the sidebar already receives (`ChatToWebview` in `app/main/ipc.ts`), so each reaction is true: waiting on the model (`busy`, after `assistantStart`, before the first `assistantDelta`), writing (`assistantDelta`), working (a `toolCall` entry with no `toolResult` yet), needs you (`approvalRequest`, or `state.pendingApproval` on replay), finished (`busy` back to `false`) and error (an `entry` of kind `error`). Blinking, an idle bob and occasional look-around run on top of those states.
    - **Expressions are data.** A pure state → expression module, where each expression is a table of eye, brow and mouth shapes, is unit-tested without a DOM, following the `transcriptStoreCore.ts` core/glue split. The DOM layer only applies it.
    - **Quiet by default.** Kraty never opens, focuses, sounds or pops up by itself. It is off until the user enables a single row under **Settings ▸ LLM Assistant**. Unprompted tips ("it looks like you're…") are *not* part of this item; they would need their own item and rules.
    - **Presentation only.** Any speech bubble shows fixed `t()` strings from `app/shared/i18n/en.json` and `es.json`. Model, tool and conversation text never reaches it, and the face reads only the state signals above.
    - **Fits the chat page.** Animation is class-driven, because the page's CSP is `style-src kkss:` and allows no `style=` attributes. `prefers-reduced-motion` keeps the expression changes and drops the idle motion. The avatar is `aria-hidden` and not focusable, and its loop stops while the sidebar is hidden.
    *Chat parity:* none. The face renders state the sidebar already has, and the model neither needs nor sees it, so the system prompt, `toolPolicy.ts` and the context suffix stay unchanged. *Docs:* `getting-started.md`'s AI assistant section, `development.md`'s AI chat sidebar section, `configuration.md`'s LLM assistant section, a `CLAUDE.md` line for the presentation-only rule, and `npm run docs:screenshots` so the sidebar shots show it. *Verification:* a `test/` unit case for the state mapping, and `tools/e2e/accessibility.mjs` must keep the chat page clean in all four themes.

## Non-goals / known constraints

- **Keeping app-specific submodule patches uncommitted or on a release branch** — shared workflow contracts can require upstream changes; commit those on the designated integration branches and move the parent gitlinks only to their committed revisions.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image is a separate tag of a separate distribution, and the installer stays lean.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image), the authenticated web front end and a reference per-user orchestrator so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 18 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once.
- **Model-enabled extensions** — the assistant may draft a skill, template or hook for the user to review and save, but it never trusts a folder, enables a server or turns a hook on. A hook runs before every approval, and a tool result that could switch one on would let the model approve its own calls. Enabling is a user action in the manager.
- **Vendor CLI extensions on the subscription runtimes** — the Claude Code and Codex plugin, hook, skill and MCP systems stay off (`settingSources: []`, `plugins: []`, `strictMcpConfig`, `CODEX_RESTRICTIONS`). Each would be a second gate the approval flow cannot see, so KKSS definitions reach those runtimes only through `executeTool`.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **9 → 7, 8.** The meta server's allow-list and path scoping both classify through `toolPolicy.ts`; without Kratos rows every Kratos tool would be refused (7) or always prompt (8).
- **13 → 15.** Remote staging reuses the cloud layer's watcher and write-back; an export tree (a results directory, an OpenFOAM case) is the normal remote case, so nested-tree write-back must exist first.
- **3 → 15.** Remote solves only become reviewable if result discovery has live acceptance for generated-case output settings rather than assuming a local `vtk_output/`.
- **18 → 20.** The remaining sharing and resize validation must be settled before the container and hardware acceptance checks can close.
- **7 → 23.** User-server tools must stay out of the HTTP meta server until its allow-list exists, because its raw call path is un-gated.
- **23 → 24, 25.** Project-folder instructions, skills and hooks all need the folder-trust record that item 23 introduces.
