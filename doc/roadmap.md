# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two unmodified VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* verbatim behind a fake `vscode` module — with OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over three MCP servers whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running — and whose image results are shown in the sidebar, a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** The zero-modification invariant means a change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for the MCP servers, `application-downstream` for extension code) plus a gitlink bump here — never a local patch, and never the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

## Queued

### Tier 0 — Submodules stay current

*Admission: keeping `cad/` and `mesh/` at their latest release, with the features they gain actually reachable from the app.*

1. **Gitlink currency, with the mirror checklist a bump actually requires** (**S** per bump, recurring). Both submodules must track their latest release and the new features must be *integrated*, not merely present in the tree — a bump that builds is not a bump that works. The full checklist lives in `doc/guide/development.md` under **Submodule release maintenance**: review the upstream notes and diff on the right branches (`kkss.dev` for MCP changes, `application-downstream` for extension code); run `npm run package --prefix mesh` before the parent build and confirm `out/meshio/dist/meshioplusplus_wasm*` lists all four files; mirror `tools/webviewMarkup.ts`'s mesh body element for element against `buildPreviewHtml`; extend `vscodeShim.ts` rather than patching, and give menubar-only actions native menu routes; classify new MCP tools in `toolPolicy.ts`; build the CAD MCP kernel via `cadMcpWorkerConfig`, never copy upstream's artifact; then typecheck, test, smoke, docs and screenshots. *Chat parity:* a new viewer or file capability is only useful to the assistant if the submodule's own MCP server exposes it — if it doesn't, that is upstream work on the submodule's `kkss.dev` branch, and the gitlink bump waits for it. A new **app-level** ability arriving with the bump needs the system-prompt description updated in the same change.

### Tier 1 — Tutorials and worked examples

*Admission: closes a gap between what the app can already do and what a new user is shown how to do — the guide pages document each mode in isolation, but nothing connects them into the single geometry-to-results pipeline the app exists for.*

2. **An end-to-end "geometry to results" tutorial** (**M**). `doc/guide/cad-mode.md` and `doc/guide/mesh-mode.md` each document their own mode's toolbar in isolation, and `getting-started.md` covers app chrome, not workflow — nothing connects them into the single pipeline the app exists for. A new user has no page that starts at "sketch or import a solid" and ends at "read off the stress field," even though every step already works end to end: build or import geometry and mesh it with Gmsh in CAD mode, export to `.mdpa`, open it in mesh mode, use the Problemtype sidebar (a built-in — Structural, Fluid, Convection-Diffusion, Potential Flow, Shallow Water — or the Flowgraph node editor) to assign materials and boundary conditions, **Generate** the ProjectParameters.json + materials file(s) + MainKratos.py, **Run** it in the embedded terminal, and **Open results** back into the viewer's VTK timeline. Ship it as `doc/guide/tutorial-*.md` pages (added to `.vitepress/config.ts`'s nav and sidebar) built around one small, reproducible worked example per physics domain — start with a structural cantilever, matching whatever fixture already ships under `cad/`'s or `mesh/`'s own example trees rather than inventing new geometry — with the walkthrough's screenshots produced by `npm run docs:screenshots` (`tools/screenshots.mjs`) like every other doc image, never hand-captured. Writing it needs a local Kratos install to actually exercise the **Run** step (the app doesn't bundle one); the app-local uv bootstrap now provides the tool-server launcher, but the manual Run step still needs a usable Kratos Python environment. *Chat parity: none directly* — but the same worked example is the natural seed for item 3 below, and for eventually showing the assistant drive the pipeline via the `cad__*`/`mesh__*`/`kratos__*` MCP tools as an alternative to the manual sidebar flow.

3. **A "using the AI assistant to run a simulation" tutorial** (**S**, depends on item 2). Once the manual pipeline is documented, a companion page shows the same pipeline driven conversationally instead — "import this STEP file, mesh it, set up a structural case, run it, tell me the max displacement" — which is the only place today that would make the chat sidebar's actual value legible: `getting-started.md`'s "AI assistant" section documents the sidebar's *chrome* (provider settings, MCP client mode) but has no worked prompt. Tool-call approval has shipped, so the walkthrough can show the real approve/deny prompt — including **Validate (dry run)** on the cad tools that support it — rather than a screenshot that goes stale the moment it lands. Image results render in the sidebar too, so a `render_snapshot` step can show what the assistant actually looked at. Transcript persistence has shipped, so the example can be a saved conversation a reader is pointed at rather than a one-off screenshot. *Chat parity: this **is** chat-surface documentation — keep its prompts and tool names in sync with `chatService.ts`'s system-prompt capability description whenever that changes.*

### Tier 2 — Distribution and deployment

*Admission: the app builds and ships correctly, but is not yet easy to install, trust, or reach. Nothing in this tier is a prerequisite for anything above it.*

4. **File associations and a `kkss://` protocol handler** (**S**). `electron-builder.yml` declares no `fileAssociations` and no `protocols`, so double-clicking a `.mdpa`, `.stp` or `.vtk` never reaches KKSS on any platform — the app can only ever be started first and asked to open a file second. The behavior behind the declarations already exists: the single-instance lock forwards a second launch's argv (and macOS `open-file`) into the running app, which is what every association handoff on Windows and Linux relies on. So this is now just the declarations plus their plumbing. Pair with item 8's MIME registration on Linux, and keep the association list aligned with `app/main/router.ts`'s real routing table rather than a hand-written duplicate. *Chat parity: none* (packaging).

5. **macOS signing, notarization and hardened runtime** (**M**). The `mac:` block targets `dmg` + `zip` with no `hardenedRuntime`, no `entitlements`, and no notarization step in `.github/workflows/release.yml`, so a downloaded build is Gatekeeper-blocked on any clean machine — and `updates.ts`'s own header already records that the unsigned macOS builds fall back to the releases page. Needs a Developer ID certificate and an app-specific password or App Store Connect API key in CI secrets, entitlements for the JIT and unsigned-memory the Electron/WASM stack requires, and a notarize+staple step on both artifacts. Note the interaction with `asar: false`: every file in the package is signed individually, which makes signing measurably slower on this tree. *Chat parity: none* (packaging).

6. **Update coverage beyond NSIS and AppImage, plus release channels** (**S–M**). `canAutoUpdate()` gates in-app download+install to those two formats; deb, dmg and zip users are told to visit the releases page. Some of that is inherent (a `.deb` should be updated by the system package manager — which argues for publishing an apt repo rather than an in-app updater), and some is item 5's blocker (macOS auto-update needs signing). Separately, there is no channel concept at all: any tagged release becomes the update every user is offered, so a pre-release cannot be published without shipping it to everyone. Add a channel to the feed and a Settings toggle for opting into pre-releases. *Chat parity: none* (packaging).

7. **Harden the streamed-desktop image's defaults** (**S**). `docker/entrypoint.sh` starts `x11vnc` with `-shared` and, unless `VNC_PASSWORD` is set, `-nopw`; websockify then serves noVNC over plain HTTP. So the default deployment is an unauthenticated desktop, and `-shared` means a second viewer joins the *first one's session* — same cursor, same windows — rather than getting their own. That is a reasonable single-user dev-box default and a poor default for anything reachable beyond localhost. Wanted: a password when none is supplied — generated at start and printed once to `docker logs` with the URL, the same shape as the meta server's bearer token — instead of `-nopw`; an explicit `-noshared`/session-scope decision, with the "one container is one session" statement made in the entrypoint and both compose files rather than only in the guide; and websockify bound to loopback behind whatever fronts it. This is the *floor*: a real login (item 9) and TLS (item 10) sit on top and are scoped separately so this can land first. Note the invariant this must not break: the entrypoint's Electron flag set stays in sync with `tools/smoke.e2e.mjs`/`tools/e2eShared.mjs`. *Chat parity: none* (deployment).

8. **Linux packaging breadth** (**S**). `linux.target` is `AppImage` + `deb`. Adding `rpm` (Fedora/openSUSE) and, separately, evaluating Flatpak — which interacts badly with `asar: false` plus a compiled native module, so it needs a real probe before being estimated — widens reach for the scientific-Linux audience this app targets. Ship the desktop-entry MIME registration here alongside item 4 so the association actually resolves on Linux. *Chat parity: none* (packaging).

### Tier 3 — Web service

*Admission: turns the streamed-desktop image from a localhost dev box into something one can hand other people a URL to — authenticated, encrypted, isolated per user, and usable without a shell into the container. Everything here builds on item 7 and nothing here blocks anything above it. The unit of deployment stays the unmodified image: every item is an entrypoint, compose, proxy or app-level change, never a fork of the app for the web.*

9. **A login in front of the stream** (**M**). The only credential today is `VNC_PASSWORD`, and it is the wrong kind: RFB "VNC authentication" is a DES challenge that uses the first eight characters of the password, it is typed into noVNC's own prompt rather than a page the operator controls, there is no notion of *who* logged in, no logout, and no rate limit — so brute-forcing an eight-character secret against a port on the internet is a matter of hours. Wanted: an HTTP authentication layer in the runtime stage that fronts websockify, so the published port belongs to the proxy and websockify joins x11vnc on loopback. Two credential sources, both operator-provisioned: a local user list (`KKSS_AUTH_USERS` as `user:bcrypt-hash` pairs, or a mounted htpasswd file — never a plaintext password in `environment:`), and OpenID Connect (`KKSS_OIDC_ISSUER`/`_CLIENT_ID`/`_CLIENT_SECRET` plus an allowed-emails or allowed-groups list) so a lab or company SSO works without KKSS storing passwords at all. With neither configured, generate a one-time password and print it with the URL, the way item 7 does for the VNC layer. The VNC password itself becomes an *internal* secret — generated per container start and handed to noVNC through websockify's token plugin or the `password` URL parameter, never shown to the user — so a login is one step, not two. Candidate implementations, all AGPL-compatible: Caddy (Apache-2.0; basic auth and forward-auth built in, and item 10's TLS for free), nginx (BSD-2), and oauth2-proxy (MIT) for the OIDC half; pick one and record why the others were rejected. Must keep: the non-root user (the proxy binds an unprivileged port), the `wait -n` supervision (the proxy is one more tracked child), the healthcheck (which then probes the proxy and needs either credentials or an unauthenticated `/healthz`), and a `docker.yml` boot check asserting a 401 without credentials and a 200 with them (item 18). Rewrites the Caveats and Access sections of `doc/guide/web-deployment.md`. *Chat parity: none* (deployment) — but see item 12 for what a login makes possible.

10. **TLS termination and a reverse-proxy recipe** (**S**, mostly free if item 9 picks Caddy). noVNC is served over plain HTTP and the stream runs over `ws://`; the guide says "prefer a reverse proxy with TLS + auth" and ships no recipe, and item 9's login form would otherwise send a password in the clear. Wanted: in-image TLS when the operator provides a certificate (`KKSS_TLS_CERT`/`KKSS_TLS_KEY` mounts) or a public hostname for ACME (`KKSS_PUBLIC_URL` — Caddy issues and renews Let's Encrypt certificates by itself), HSTS on by default when TLS is on, and a documented compose overlay for the "we already have Traefik/nginx in front" case that gets right the two things such setups classically break: the WebSocket `Upgrade`/`Connection` headers and a long proxy read timeout, since the stream is one idle-looking connection. Localhost stays plain HTTP on purpose: a self-signed certificate warning on `localhost:6080` is worse than what ships today. *Chat parity: none* (deployment).

11. **Session lifecycle: idle timeout, graceful stop, and a bookmarkable reconnect** (**S–M**, one half possibly defect-shaped). Three gaps. (a) Nothing ends a session: a closed browser tab leaves SwiftShader rendering to nobody, which on a shared host is the CPU budget of the next user. websockify's `--idle-timeout` ends the container through the existing `wait -n` supervision once no client has been connected for `KKSS_IDLE_TIMEOUT` seconds, and `restart: unless-stopped` brings it back cold — acceptable only if the stop below is clean. (b) `docker stop` forwards SIGTERM to every child, but the entrypoint's `drain()` waits 3 s (30 × 0.1 s) and then exits, at which point tini takes the container down — while the app's own `before-quit` cloud-upload drain is capped at 10 s and the `flushSync()` of `state.json` runs after it. Worse, a quit passes through `main.win.on("close")`, which is where the dirty-mesh-tab **Save / Don't Save / Cancel** prompt lives (`confirmDiscardMeshTab`); in a headless container nobody answers it, and the 20 s `stop_grace_period` ends in SIGKILL with the edit lost. Whether a SIGTERM-driven quit runs those hooks at all is the first thing to establish; if it does, this half is a data-loss finding and moves to a recreated Tier 0 entry per this file's own rule. The fix shape is known either way: drain for the app's real budget rather than 3 s, and a `KKSS_HEADLESS=1` gate (or detection of no interactive user) that resolves the prompt as "save and quit" instead of blocking on it. (c) Reconnect: a reload of `vnc.html` does re-attach to the same X display, but with `autoconnect`, `resize=remote` and item 9's token in the URL it becomes a bookmarkable page rather than a Connect button plus a password prompt — ship that as the landing URL the entrypoint prints. `resize=remote` is also the door to lifting the guide's *fixed display size* caveat: it needs a RANDR-capable server, and the probe is swapping Xvfb + x11vnc for TigerVNC's `Xvnc` (GPL-2.0; one process that is both the display and the VNC server, and resizes the desktop to the browser on request), which also removes one process from the supervision chain. *Chat parity: none* (deployment).

12. **Operator-provisioned configuration and secrets** (**S–M**). Everything the app persists — theme, zoom, LLM provider and API key, the meta MCP server toggle and bearer token, cloud client IDs — is set through the Settings menu and lands in `state.json` on the userdata volume, where the API key is safeStorage-"encrypted" with the basic backend since the container has no keychain, i.e. readable by anyone holding the volume (the guide's own caveat). A web deployment inverts who owns those settings: the operator pays for the key and does not want it on a per-user volume or typed into a streamed desktop. Wanted: environment and secret-file overrides (`KKSS_LLM_PROVIDER`, `KKSS_LLM_MODEL`, `KKSS_LLM_API_KEY_FILE` for `docker secrets`, `KKSS_PROJECT_ROOT=/workspace`, `KKSS_RESTORE_SESSION=0`, …) resolved at startup in `stateStore`'s own shape, taking precedence over the stored value and never written back to the volume — so the key exists in memory and nowhere on disk. `KKSS_E2E`/`KKSS_NO_RESTORE` are already environment gates read in `index.ts`, so the mechanism has precedent; only the surface is new. *Chat parity: yes* — the **Settings ▸ LLM Assistant** menu shows a managed value greyed out as *set by the environment* rather than editable; the assistant itself has no settings tool, so the system prompt is untouched.

13. **Files in and out of a browser session** (**M**). The in-app dialogs browse the container filesystem, so the only way to get a model into a web session today is a bind mount arranged by whoever runs Docker — the person in the browser cannot, and noVNC has no file transfer. Wanted: a file bridge behind item 9's login on the same origin — a small file manager (filebrowser, Apache-2.0) rooted at `/workspace` under `/files/`, giving upload, download, and drag-and-drop of a whole case directory (`.mdpa` + `ProjectParameters.json` + materials + the results tree), and a "download results" path for a VTK series and the generated sidecars — plus a *Files* entry in the noVNC sidebar or the KKSS home screen that opens it in a new tab. The app side is nil: an uploaded file is a file under `/workspace`, which the Open dialog and `services/projectRoot.ts`'s default already see. Keep it a sidecar, not a KKSS feature — the desktop app has a real filesystem and needs none of this. *Chat parity: none* — the assistant already reaches `/workspace` through the MCP tools.

14. **Cloud accounts from a browser session** (**S–M**). The cloud staging layer (Drive/Dropbox/OneDrive) is the natural way for a web user to bring their own files — and it cannot be connected in the container. `services/cloud/oauth.ts` opens the provider's consent page with `shell.openExternal` (the image ships no browser) and completes on a one-shot `127.0.0.1` loopback redirect *inside the container*; a user who opens the URL on their own machine is redirected to their own localhost, where nothing listens. Wanted: a "no browser" leg of the flow, the shape `gcloud auth login --no-browser` uses — the app shows the consent URL to copy, and a field to paste the full redirected `http://127.0.0.1:…/callback?code=…&state=…` URL back into, from which it extracts code and state and continues the exact PKCE exchange it does today. Offer it as an always-present alternative button rather than gating on headless detection, keep the `state` check, and change nothing in the provider layer: this is the redirect leg only. *Chat parity: none* (a document opened from the cloud is already an ordinary staged path to the assistant).

15. **A Kratos-enabled image variant** (**M**). Two of the three chat tool servers work in the container; the Kratos one does not, because `uvx` is not shipped — and the embedded terminal has no Kratos either, so the Run step of the tutorial (item 2) and the Jobs panel are dead ends in the browser, which is precisely where a "try Kratos without installing anything" deployment is most valuable. Wanted: a second published tag (`ghcr.io/loumalouomega/kkss:<version>-kratos`) built from the same Dockerfile with a build arg, whose runtime stage adds uv into the `kkss` user's home (the app-local layout `kratosRuntime.ts` probes first, so no PATH change), a pre-resolved `kratos-mcp-server` at the pinned `KRATOS_MCP_VERSION` so first use does not download, and a KratosMultiphysics install carrying the applications the built-in Problemtypes generate cases for (Structural, Fluid, Convection-Diffusion, Potential Flow, Shallow Water). The base image stays lean and the desktop installer stays Kratos-free (Non-goals); the variant is a distribution, not a bundle. `docker.yml` gains a second matrix dimension, and its boot check runs the Kratos MCP handshake the Linux CI already proves. The license check applies to everything the variant installs (Kratos is BSD-licensed and installed as an independent package, not linked). *Chat parity: none new* — the tools already exist, and the context suffix already reports their availability.

16. **Real-GPU rendering as an opt-in** (**S–M**, *needs a probe before it can be estimated*). The image renders through SwiftShader by design — that is the configuration CI proves — and the guide's caveats ("very large meshes render slowly", "the WebGL renderer can occasionally crash mid-frame") are the price. A host with a GPU should be able to lend it: `KKSS_GPU=1` mounts `/dev/dri` and swaps the SwiftShader flags for EGL on the host driver, or VirtualGL for the Xvfb-with-GLX case. The invariant is that the *default* flag set stays byte-identical to `tools/e2eShared.mjs`; the GPU set is a documented, separately named alternative, never a drift of the default. Also the place to revisit the Mesa/`libgbm` versions in the runtime stage. *Chat parity: none* (deployment).

17. **Per-user sessions: one container per login, with a reference orchestrator** (**L**, depends on 9, 11, 12). One container is one session, and item 7 makes that explicit; a second person gets the first person's desktop. The guide's SaaS outlook names the shape (Kasm Workspaces, or a proxy plus a session broker) and ships none of it. Wanted: a small session broker as its own service under `docker/broker/` — on an authenticated login (item 9's identity) it starts the published image with a per-user `/workspace` and userdata volume (item 12 injecting that user's settings), routes `/s/<session>/` to that container's stream, idles it out (item 11), enforces a per-user and a global container cap, and lists and stops a user's sessions on a plain page — delivered as a `docker-compose.multi.yml` with Traefik or Caddy doing path routing, plus one Kubernetes manifest for the "we already have a cluster" reader. The image needs exactly two things from this: a `KKSS_BASE_PATH` so noVNC and websockify work behind a path prefix, and an idle signal the broker can read (a `/healthz` reporting the connected-client count is enough). *Operating* such a deployment — accounts beyond what the OIDC provider supplies, billing, quotas, backups of user volumes — stays out of scope (Non-goals). *Chat parity: none* (deployment).

18. **Web-service checks in CI** (**S**). `docker.yml` boot-checks that noVNC answers, the display is up and the app process is alive — a black screen over a live process passes. Wanted, growing with the items above: assert that `OPEN_FILE` actually opened (the window title carries the file name, and `xdotool search --name` inside the container reads it, as the entrypoint's sizing helper already does); a 401/200 pair through the login (item 9); a `docker stop` that exits 0 inside the grace period with `state.json` intact (item 11); the Kratos handshake on the `-kratos` variant (item 15); and a vulnerability-scan gate that fails a *branch* build, not only a tag push, since the runtime `apt-get upgrade` comment in the Dockerfile already records that release-time-only surprise. *Chat parity: none* (CI).

### Tier 4 — Verification and quality

*Admission: closes a gap between what is asserted automatically and what only a human currently notices. Ranked last deliberately; nothing here blocks anything above.*

19. **Broaden the e2e harness** (**M**). `tools/smoke.e2e.mjs` launches the real app and asserts three host↔webview handshakes — cad STEP, mesh MDPA, mesh VTK — plus packing-menu availability after file open and CAD/mesh switches. Broader coverage is still needed for the home screen, text editor, terminal, chat sidebar, zoom, menu dispatch, screen switching, the tab strip and the meta MCP server in the live app; `test/` holds glue unit tests (`router`, `watcher`, `pathGuard`, `stateStore`, `atomicWrite`, `recentFiles`, `session`, `projectRoot`, `changelog`, `updateCheck`, `preprocessArchive`, chat routing/SSE/secrets/transcript/store/service/toolPolicy, `metaServer`, `webviewPages`, the bundled CAD MCP runtime, and the cloud staging layer's `cloudCachePath`/`cloudManifest`/`cloudConflict`/`cloudOauth`/`cloudProviders`/`cloudUploadChunks`/`cloudSync`) that never start the app. `tools/e2eShared.mjs` already provides the launch and window helpers, so the incremental cost per case is small. Prioritize the paths a submodule bump can silently break: the generated webview pages mounting their expected DOM, the shim's command surface, and the pre→post export sync. The cloud staging layer adds two more that only a live app exercises: **File ▸ Open from Cloud…** being present and disabled with no account connected, and the `before-quit` upload drain. Both harnesses now launch with an isolated `--user-data-dir`, so a case may seed persisted state without touching the developer's profile — which makes the launch-time paths testable for the first time. Two deliberate gaps remain, both self-inflicted by design: the harness sets `KKSS_ALLOW_MULTIPLE_INSTANCES=1`, so the single-instance lock's own acquisition is never exercised, and it sets `KKSS_E2E`, which disables session restore — so restoring tabs/screen/panels is likewise untested end to end. Closing either means a deliberate re-enable flag for one case rather than loosening the gate. *Chat parity: none* (test infrastructure) — the stub provider and Electron stub a chat case needs already exist (`test/stubs/electron.ts`, `test/chatService.test.ts`).

20. **A launch and file-open performance baseline** (**S–M**). The CAD submodule ships `npm run perf` with a checked-in baseline and a deliberately generous tolerance; KKSS measures nothing. A submodule bump that doubles first-frame time, or a build change that adds seconds to app launch, lands unnoticed — and the two most expensive paths (OCCT parse in the compute worker, mesh load through meshio++) are exactly the ones a bump touches. Measure app launch to first interactive frame, and file-open to `geometry`/`model` for one fixture per mode, against a committed baseline; opt-in, not a CI gate, for the same machine-variance reason cad's harness gives. *Chat parity: none* (tooling).

21. **Accessibility and localization pass** (**M**, *evaluated, needs scoping before it can be estimated honestly*). The shell, home, editor and chat renderers are hand-written DOM with no ARIA roles, no asserted keyboard-only path, and no focus management across the stacked-view screen model — which is unusual enough (each screen is a separate `WebContentsView`, so focus does not move within one document) that the tab-order story needs designing, not just annotating. Every user-facing string is inline English across the renderers, the native menu, and the main process's dialogs and toasts. Listed so the size of the commitment is on record rather than discovered mid-change; the viewer surfaces inside both submodules are a separate, larger question that would be upstream work. *Chat parity: none* (UI).

## Non-goals / known constraints

- **Patching `cad/` or `mesh/` to make an app-level feature easier** — the zero-modification invariant is architectural, not a missing convenience. A genuinely unavoidable change goes to a dedicated branch in that submodule with the gitlink pointed at it, never to the submodule's default branch and never as a local edit.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature.
- **A dirty-state prompt when closing a tab** — cad and mesh have no app-level "unsaved changes" concept; their sidecars autosave on a debounce, so closing a tab is a plain dispose, exactly like replacing a tab's document has always been. Adding a prompt would mean inventing a document-dirty model the submodules don't have.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image (item 15) is not an exception: it is a separate tag of a separate distribution, and the installer stays lean.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image) and, through Tier 3, the login, TLS, session lifecycle and a reference per-user orchestrator (items 9–17) so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 7 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **2 → 3.** The chat-driven tutorial reuses the manual one's worked example and pipeline description; writing it first means describing the same pipeline twice.
- **7 → 9.** The generated-password fallback and the loopback-bound websockify are what the login layer fronts; landing the login first would mean choosing the proxy before the thing it protects has a defined default.
- **9 → 10, 17.** The login is the identity the orchestrator keys sessions on and the reason TLS exists; the proxy is chosen once, in item 9, and item 10 is nearly free or not depending on that choice.
- **11, 12 → 17.** Idle-out and environment-provisioned settings are what make a per-user container affordable and configurable without a shell; the broker consumes both rather than reinventing either.
