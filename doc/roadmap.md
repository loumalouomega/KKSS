# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two unmodified VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* verbatim behind a fake `vscode` module — with OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and chat sidebar), an LLM agent loop over three MCP servers, an optional HTTP meta MCP server that re-exposes the same toolset, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** The zero-modification invariant means a change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for the MCP servers, `application-downstream` for extension code) plus a gitlink bump here — never a local patch, and never the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

## Queued

### Tier 0 — Submodules stay current

*Admission: keeping `cad/` and `mesh/` at their latest release, with the features they gain actually reachable from the app.*

1. **Gitlink currency, with the mirror checklist a bump actually requires** (**S** per bump, recurring). Both submodules must track their latest release and the new features must be *integrated*, not merely present in the tree — a bump that builds is not a bump that works. What a bump has to re-check, because none of it is enforced by the compiler:
   - `npm run package --prefix mesh` **before** the parent build, so `mesh/dist/meshio/` is regenerated for `copyArtifacts()` to mirror.
   - `out/meshio/dist/meshioplusplus_wasm*` lists **four** files afterwards — both the sequential and the threaded pair. Shipping only the old pair makes every extended format die with an opaque `LinkError`, and nothing parent-side enumerates them.
   - `tools/webviewMarkup.ts`'s `meshBody()` is a hand-kept replica of `webviewChrome.buildPreviewHtml`'s body — mirror it element for element, and consume `webviewChrome.ts`'s exports rather than inlining markup.
   - `app/main/vscodeShim.ts` throws loudly on unsupported commands *by design*. A submodule that starts calling a new `vscode` API means extending the shim, never patching the submodule.
   - `npm run build` runs `tools/check-theme-vars.mjs`, which fails on a `--vscode-*` or `--ds-*` variable a submodule newly consumes.
   - Anything reachable **only** from the mesh viewer's hidden `#menubar` strip needs a native menu entry (that is why File ▸ Save/Load Problem… exist).

   *Chat parity:* a new viewer or file capability is only useful to the assistant if the submodule's own MCP server exposes it — if it doesn't, that is upstream work on the submodule's `kkss.dev` branch, and the gitlink bump waits for it. A new **app-level** ability arriving with the bump needs the system-prompt description updated in the same change.

### Tier 1 — Session and document model

*Admission: makes the app remember what the user was doing. These three share one piece of new persisted state; landing them out of order means building it twice.*

2. **App-wide recent files** (**S**). Half of this exists, and the missing half is the app-level half. Mesh's own `RecentMeshStore` is surfaced as **File ▸ Open Recent** (`app/main/menu.ts`, rebuilt from `onDidChange` because an Electron menu is static once built), but it is the *submodule's* store: it records only what the mesh providers open, and KKSS's menu entry hardcodes `openFile(fsPath, "mesh")`. So a CAD document opened in pre mode is remembered nowhere, and the home screen is still five static buttons (`app/renderer/home/homeConfig.ts`) with no recent list at all. Wanted: a KKSS-side `recentFiles` stateStore key (path, mode, timestamp; capped, deduplicated, pruned of paths that no longer exist) recorded from `openFile()` itself, so it covers both modes and every entry point — CLI argument, forwarded second instance, macOS `open-file`, the tab strip — feeding a home-screen list and either merging with or superseding the mesh-only submenu. *Chat parity: none directly* — but the assistant should be able to see the list once item 4 gives it a scope to describe.

3. **Session restore on launch** (**M**). Reopen the last session's tabs per mode, the last screen, and the terminal/chat visibility state. The pieces already exist — `setScreen()`, `openFile()`, `createTab()`, `toggleTerminal()`/`toggleChat()`, and a `stateStore` that already persists `uiZoom` on the same principle. Note the unit to restore is a *tab list per mode*, not one document per mode: tab ids (`windows.ts`) are per-run, so what persists is each mode's file list plus which one was focused. Two details decide whether this feels good or hostile: restore must not fight a launch-time open (a `cliFileArg()` file, or one forwarded from a second instance, wins and takes the screen), and a file that has vanished or now fails to parse must degrade to the home screen with a toast, never to a broken view. *Chat parity: none* (the assistant already receives the current files each turn).

4. **A workspace / working-directory concept** (**M**). Four features guess a root independently today, and they disagree: the terminal's cwd is `path.dirname(currentFile)` of the focused tab or `$HOME` (`TerminalService`'s `cwdProvider`), the editor's open dialog starts wherever Electron last left it, the chat's `contextSuffix()` names the open files and nothing else, and the meta MCP server hands out tools that can read and write anywhere the app can. One explicit project root — chosen once, persisted, shown in the shell — would unify all four, make **Open Recent** meaningfully grouped, and give item 6 the scope boundary its approval rules need ("anything under the project root" is a rule a user can reason about; "anything on disk" is not). *Chat parity: the root belongs in the context suffix, not the system prompt (it is volatile), and the meta server's tool-exposure warning in the "Copy Address & Token" dialog should say what the root is.*

### Tier 2 — AI assistant depth

*Admission: the agent loop already works end to end; these make it trustworthy, reviewable, and durable. Nothing here needs a new MCP server.*

5. **Transcript persistence and multiple conversations** (**M**). `ChatService.entries` is an in-memory array with no disk backing. Quitting the app discards the entire conversation, and **New Chat** does the same with no confirmation and no way back — including the tool calls that document what was actually done to the user's files, which is often the only record. Persist per conversation (transcripts can be large: tool results are capped at `RESULT_CHARS` = 50 000 each, so a store keyed by conversation with lazy loading beats one growing JSON blob), list them in the sidebar, and keep the wire form's existing truncation so the renderer never receives the full text. *Chat parity: this **is** the chat.*

6. **Tool-call approval and dry-run gating** (**M**). Every tool call the model emits executes unconditionally — `chatService.ts`'s loop goes straight from `result.toolCalls` to `mcp.callTool()` — and those tools write sidecar files, overwrite meshes, and start simulations. The app already understands the risk: enabling the HTTP meta server pops a dialog warning that *"these tools read and write files on disk and can run simulations. Only share this address and token with a client you trust."* The built-in agent, which runs the same aggregated toolset, has no equivalent gate. Wanted: a per-tool read/write classification (the MCP tool list is discovered at runtime, so this needs a policy table plus a conservative default for unknown tools), an approve/deny prompt inline in the transcript, and a remembered "always allow this tool in this conversation". Pairs naturally with item 4: auto-approve inside the project root, ask outside it. *Chat parity: this is chat surface; the policy also belongs on the meta server's HTTP side, which today has only the bearer token.*

7. **Token, cost and context visibility** (**S–M**). The only bounds today are `MAX_ITERATIONS = 25` and the per-result `RESULT_CHARS` truncation. Nothing reports how much context a conversation is using, nothing estimates spend, and nothing compacts a long transcript — so a long session either silently approaches the model's context limit or fails at the provider with a message the sidebar renders as a generic error banner. Note this is bigger than it looks: neither `providers/anthropic.ts` nor `providers/openaiCompat.ts` parses the usage figures the APIs return today, so the provider layer needs to surface usage before the header can display it. Then show it next to the existing provider label, and add explicit compaction rather than letting the window fill. *Chat parity: chat surface.*

8. **Images in the chat** (**S**). `cad__render_snapshot` returns headless multi-view PNGs, and `cad__compare_models` with `includeSnapshots` returns up to eight labelled images — real MCP image content blocks, which `mcpManager.ts` already receives. `app/renderer/chat/chat.ts` has no image path at all (no `<img>`, no data-URI handling), so the single most useful verification tool the assistant has is invisible to the user: it can look at a model and the user cannot see what it looked at. Cheaper than it looks: `app/renderer/chat/index.html`'s CSP **already** allows `img-src kkss: data:`, so no CSP change is needed (and none should be made — the rest of that policy is deliberately strict). What is needed is a wire-form change (`ChatWireEntry`'s `toolResult` carries a truncated text preview only, so image blocks are dropped before they reach the renderer), a size cap, and a decision about whether images persist into item 5's stored transcript. *Chat parity: chat surface.*

9. **Background-job surface for Kratos runs** (**M**). `kratos-mcp-server` runs simulations as background jobs, and the app has nowhere to show one: no job list, no progress in the shell's toast/status line, no way to cancel. The single guard is `CALL_TIMEOUT_MS` (10 minutes) in `mcpManager.ts`, after which a legitimately long solve returns to the model as a failed tool call while the job itself keeps running. Wanted: a jobs panel or a persistent shell status entry fed by the server's own job-status tools, polled while running, with cancel wired to whatever the server exposes; and a longer (or per-tool) timeout for the tools that legitimately need it. *Chat parity: the system prompt should tell the assistant to start jobs and poll rather than block a tool call — a prompt change, so batch it with another prompt edit where possible.* Blocked in practice by item 14 — none of this matters while the server can't start.

### Tier 3 — Tutorials and worked examples

*Admission: closes a gap between what the app can already do and what a new user is shown how to do — the guide pages document each mode in isolation, but nothing connects them into the single geometry-to-results pipeline the app exists for.*

10. **An end-to-end "geometry to results" tutorial** (**M**). `doc/guide/cad-mode.md` and `doc/guide/mesh-mode.md` each document their own mode's toolbar in isolation, and `getting-started.md` covers app chrome, not workflow — nothing connects them into the single pipeline the app exists for. A new user has no page that starts at "sketch or import a solid" and ends at "read off the stress field," even though every step already works end to end: build or import geometry and mesh it with Gmsh in CAD mode, export to `.mdpa`, open it in mesh mode, use the Problemtype sidebar (a built-in — Structural, Fluid, Convection-Diffusion, Potential Flow, Shallow Water — or the Flowgraph node editor) to assign materials and boundary conditions, **Generate** the ProjectParameters.json + materials file(s) + MainKratos.py, **Run** it in the embedded terminal, and **Open results** back into the viewer's VTK timeline. Ship it as `doc/guide/tutorial-*.md` pages (added to `.vitepress/config.ts`'s nav and sidebar) built around one small, reproducible worked example per physics domain — start with a structural cantilever, matching whatever fixture already ships under `cad/`'s or `mesh/`'s own example trees rather than inventing new geometry — with the walkthrough's screenshots produced by `npm run docs:screenshots` (`tools/screenshots.mjs`) like every other doc image, never hand-captured. Writing it needs a local Kratos install to actually exercise the **Run** step (the app doesn't bundle one); item 14 is what makes that step this easy for a *reader* too, not just the tutorial's author. *Chat parity: none directly* — but the same worked example is the natural seed for item 11 below, and for eventually showing the assistant drive the pipeline via the `cad__*`/`mesh__*`/`kratos__*` MCP tools as an alternative to the manual sidebar flow.

11. **A "using the AI assistant to run a simulation" tutorial** (**S**, depends on item 10). Once the manual pipeline is documented, a companion page shows the same pipeline driven conversationally instead — "import this STEP file, mesh it, set up a structural case, run it, tell me the max displacement" — which is the only place today that would make the chat sidebar's actual value legible: `getting-started.md`'s "AI assistant" section documents the sidebar's *chrome* (provider settings, MCP client mode) but has no worked prompt. Best written after item 6 (tool-call approval and dry-run gating) lands, so the walkthrough shows the real approve/deny UI rather than a screenshot that goes stale the moment that ships, and after item 5 (transcript persistence) so the example is a saved conversation a reader can be pointed at rather than a one-off screenshot. *Chat parity: this **is** chat-surface documentation — keep its prompts and tool names in sync with `chatService.ts`'s system-prompt capability description whenever that changes.*

### Tier 4 — Distribution and deployment

*Admission: the app builds and ships correctly, but is not yet easy to install, trust, or reach. Nothing in this tier is a prerequisite for anything above it.*

12. **File associations and a `kkss://` protocol handler** (**S**). `electron-builder.yml` declares no `fileAssociations` and no `protocols`, so double-clicking a `.mdpa`, `.stp` or `.vtk` never reaches KKSS on any platform — the app can only ever be started first and asked to open a file second. The behavior behind the declarations already exists: the single-instance lock forwards a second launch's argv (and macOS `open-file`) into the running app, which is what every association handoff on Windows and Linux relies on. So this is now just the declarations plus their plumbing. Pair with item 17's MIME registration on Linux, and keep the association list aligned with `app/main/router.ts`'s real routing table rather than a hand-written duplicate. *Chat parity: none* (packaging).

13. **macOS signing, notarization and hardened runtime** (**M**). The `mac:` block targets `dmg` + `zip` with no `hardenedRuntime`, no `entitlements`, and no notarization step in `.github/workflows/release.yml`, so a downloaded build is Gatekeeper-blocked on any clean machine — and `updates.ts`'s own header already records that the unsigned macOS builds fall back to the releases page. Needs a Developer ID certificate and an app-specific password or App Store Connect API key in CI secrets, entitlements for the JIT and unsigned-memory the Electron/WASM stack requires, and a notarize+staple step on both artifacts. Note the interaction with `asar: false`: every file in the package is signed individually, which makes signing measurably slower on this tree. *Chat parity: none* (packaging).

14. **`uv` / `uvx` bootstrap for the Kratos tools** (**M**). `mcpManager.ts` spawns `uvx kratos-mcp-server@0.3.0`, and its own header documents the failure mode: *"failure of any single server (typically kratos when uv is not installed) marks it unavailable and the chat continues with the remaining tools."* On a fresh desktop install `uv` is absent by default, so the flagship third of the toolset — project scaffolding, running simulations, ProjectParameters introspection — is silently missing, and the only signal is a grey status chip in the sidebar. Wanted: detect the situation precisely (missing `uv` versus a failed package resolve versus a network block), explain it in the chat's server-status area rather than a tooltip, offer a one-click install of `uv` into the app's own data directory, and re-probe without restarting the app. *Chat parity: the status surface is chat surface; `ChatServerStatus.error` already exists and is under-used.*

15. **Update coverage beyond NSIS and AppImage, plus release channels** (**S–M**). `canAutoUpdate()` gates in-app download+install to those two formats; deb, dmg and zip users are told to visit the releases page. Some of that is inherent (a `.deb` should be updated by the system package manager — which argues for publishing an apt repo rather than an in-app updater), and some is item 13's blocker (macOS auto-update needs signing). Separately, there is no channel concept at all: any tagged release becomes the update every user is offered, so a pre-release cannot be published without shipping it to everyone. Add a channel to the feed and a Settings toggle for opting into pre-releases. *Chat parity: none* (packaging).

16. **Harden and generalize the streamed-desktop image** (**M**). `docker/entrypoint.sh` starts `x11vnc` with `-shared` and, unless `VNC_PASSWORD` is set, `-nopw`; websockify then serves noVNC over plain HTTP. So the default deployment is an unauthenticated desktop, and `-shared` means a second viewer joins the *first one's session* — same cursor, same windows — rather than getting their own. That is a reasonable single-user dev-box default and a poor default for anything reachable beyond localhost. Wanted: authentication on by default (generate a password when none is supplied and print it once, the same shape as the meta server's bearer token), TLS guidance or a reverse-proxy recipe in `doc/guide/web-deployment.md`, an explicit `-noshared`/session-scope decision, and a documented statement that one container is one session. Note the invariant this must not break: the entrypoint's Electron flag set stays in sync with `tools/smoke.e2e.mjs`/`tools/e2eShared.mjs`. *Chat parity: none* (deployment).

17. **Linux packaging breadth** (**S**). `linux.target` is `AppImage` + `deb`. Adding `rpm` (Fedora/openSUSE) and, separately, evaluating Flatpak — which interacts badly with `asar: false` plus a compiled native module, so it needs a real probe before being estimated — widens reach for the scientific-Linux audience this app targets. Ship the desktop-entry MIME registration here alongside item 12 so the association actually resolves on Linux. *Chat parity: none* (packaging).

18. **Cloud-storage provider compatibility (Drive, Dropbox, OneDrive, …)** (**S** for what already works plus a hardening fix, **L** for real in-app integration). Two different features hide under this one request, and they cost nothing alike. **Opening a file from an OS-level synced folder already works today, with zero code changes**: `dialog.showOpenDialog`/`showSaveDialog` (`app/main/services/dialogs.ts`, the sole picker surface used by `EditorService.open()`, `cadHost.ts`, and the native menu) browse into `~/Google Drive/`, `~/Dropbox/` or a OneDrive folder exactly like any other local directory, because that is all a desktop sync client actually is — a regular directory the OS keeps in sync in the background. `kkss-file://local/<enc>` (`app/main/protocol.ts`) and `pathGuard.ts`'s allow-listing (`allowRoot(path.dirname(fsPath))`, called per-document in `cadHost.ts`) are pure local-path string logic and don't care where the directory is mounted from. The one real gap is that cad's debounced sidecar autosave (`cadHost.ts`'s `AUTOSAVE_DEBOUNCE_MS` timers) writes `.parts.json`/`.edits.json` siblings with a plain `fs.writeFile`, non-atomically, straight into that watched directory — so a sync client can upload a half-written sidecar, or throw a "conflicted copy" if KKSS and the sync daemon touch the file close together. Fix: give the sidecar writer the same temp-file-then-`rename()` treatment `services/jsonStore.ts` already gives the state store, and document that any local directory under active third-party sync is a supported project location. **Real in-app provider integration (an OAuth-driven Drive/Dropbox picker and upload/download, no desktop sync client required) is the expensive, separate ask.** Every consumer of an opened path assumes a real file already sitting on disk — `EditorService`'s direct `fs` calls, `cadHost.ts`'s `fs` + `allowRoot`, and, because the zero-modification invariant forbids touching them, the cad/mesh MCP servers' own `node:fs/promises` calls in `cad/src/mcpTools.ts` and the sibling-path sidecar helpers in `cad/src/mcpSidecars.ts`. None of that can be taught to speak a provider API directly, so this needs a new staging layer instead: download to a local cache directory on open, `allowRoot()` the cache dir rather than the source directory, re-upload (content plus any sidecars) on save or on the same autosave debounce, and OAuth token storage mirroring `secrets.ts`'s safeStorage-encrypted pattern for the LLM API key and the meta server's bearer token. Item 4's workspace concept, if it lands first, gives this a natural place to surface "this project's root is a Drive folder" rather than inventing a second root concept. *Chat parity: the MCP servers only ever see the local staging path, so the assistant's file tools need no changes once staging exists — but `ChatDeps.currentFiles()` / the context suffix should say a file's real origin is cloud-backed, since the assistant should not assume a document's local path is stable across sessions the way it is for a plain local file.*

### Tier 5 — Verification and quality

*Admission: closes a gap between what is asserted automatically and what only a human currently notices. Ranked last deliberately; nothing here blocks anything above.*

19. **Broaden the e2e harness** (**M**). `tools/smoke.e2e.mjs` launches the real app and asserts three host↔webview handshakes — cad STEP, mesh MDPA, mesh VTK — and nothing else. The home screen, text editor, terminal, chat sidebar, zoom, menu dispatch, screen switching, the tab strip and the meta MCP server have no automated coverage at any level; `test/` holds glue unit tests (`router`, `watcher`, `pathGuard`, `stateStore`, `changelog`, `updateCheck`, `preprocessArchive`, chat routing/SSE/secrets/transcript, `metaServer`, `webviewPages`) that never start the app. `tools/e2eShared.mjs` already provides the launch and window helpers, so the incremental cost per case is small. Prioritize the paths a submodule bump can silently break: the generated webview pages mounting their expected DOM, the shim's command surface, and the pre→post export sync. One deliberate gap to close eventually: the harness sets `KKSS_ALLOW_MULTIPLE_INSTANCES=1`, so the single-instance lock's own acquisition is the one startup path e2e never exercises. *Chat parity: none* (test infrastructure) — though a chat case needs a stub provider, worth building once.

20. **A launch and file-open performance baseline** (**S–M**). The CAD submodule ships `npm run perf` with a checked-in baseline and a deliberately generous tolerance; KKSS measures nothing. A submodule bump that doubles first-frame time, or a build change that adds seconds to app launch, lands unnoticed — and the two most expensive paths (OCCT parse in the compute worker, mesh load through meshio++) are exactly the ones a bump touches. Measure app launch to first interactive frame, and file-open to `geometry`/`model` for one fixture per mode, against a committed baseline; opt-in, not a CI gate, for the same machine-variance reason cad's harness gives. *Chat parity: none* (tooling).

21. **Accessibility and localization pass** (**M**, *evaluated, needs scoping before it can be estimated honestly*). The shell, home, editor and chat renderers are hand-written DOM with no ARIA roles, no asserted keyboard-only path, and no focus management across the stacked-view screen model — which is unusual enough (each screen is a separate `WebContentsView`, so focus does not move within one document) that the tab-order story needs designing, not just annotating. Every user-facing string is inline English across the renderers, the native menu, and the main process's dialogs and toasts. Listed so the size of the commitment is on record rather than discovered mid-change; the viewer surfaces inside both submodules are a separate, larger question that would be upstream work. *Chat parity: none* (UI).

## Non-goals / known constraints

- **Patching `cad/` or `mesh/` to make an app-level feature easier** — the zero-modification invariant is architectural, not a missing convenience. A genuinely unavoidable change goes to a dedicated branch in that submodule with the gitlink pointed at it, never to the submodule's default branch and never as a local edit.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature.
- **A dirty-state prompt when closing a tab** — cad and mesh have no app-level "unsaved changes" concept; their sidecars autosave on a debounce, so closing a tab is a plain dispose, exactly like replacing a tab's document has always been. Adding a prompt would mean inventing a document-dirty model the submodules don't have.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. Item 14 improves that path rather than replacing it.
- **A hosted, multi-tenant service on top of the Docker image** — the image streams one desktop session by design. Multi-tenancy is an orchestration concern outside this repo; item 16 makes the single-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **4 → 6.** Approval gating needs a scope to approve *within* — "under the project root" is a rule a user can reason about, "anywhere on disk" is not.
- **14 → 9.** A job surface is worthless while the server providing the jobs cannot start on a default install.
- **10 → 11.** The chat-driven tutorial reuses the manual one's worked example and pipeline description; writing it first means describing the same pipeline twice.
- **5, 6 → 11.** The chat tutorial's screenshots depend on transcript persistence and approval-gating UI existing to screenshot.
