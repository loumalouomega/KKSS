# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two upstream VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* behind a fake `vscode` module — with scoped workflow-contract changes committed on their integration branches, OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over four MCP servers (CAD, mesh, Kratos and a pinned PDF reader) plus any the user adds, whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running, and optionally after the user's own lifecycle hooks have had their say — and whose image results are shown in the sidebar, a composer that attaches images and PDFs (stored with the conversation, refused up front where a provider cannot take them), a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** A change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for MCP contracts, `application-downstream` for extension code), is committed there, and is integrated here through its gitlink — never as an uncommitted patch or on the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

### Tier 0 — Defects

*Admission: behavior that is wrong today, whatever the effort. Fix before anything below.*

1. **Shutdown recovery files are written but never offered back, and nothing is checkpointed while running** (**S**). When a dirty mesh tab cannot be saved at quit, `MeshHost.saveForShutdown` (`app/main/mesh/meshHost.ts`) writes the provider's operation recipe to `<userData>/recovery/mesh-<time>-<rand>.json` plus a `.source.json` naming the original file and logs "operation recipe recovered"; the text editor's shutdown save (`services/editor.ts`) does the same for a buffer (`editor-<time>.json`). Nothing in the app ever reads `<userData>/recovery/` (`index.ts`'s quit path only writes it), so the recovered work is invisible unless the user finds the log line — and a crash or power loss, which never reaches the quit path, loses unsaved mesh operations and editor buffers outright, because KKSS has no hot-exit analogue (`meshHost.ts` passes `backupId: undefined`). Fix in two parts, after ElmerStudio's `core/recovery.py`: (a) on launch, list recovery entries and offer each through a Home notice (Restore into a new tab / Show file / Discard) — never auto-apply, and keep an entry until the user decides; (b) checkpoint dirty mesh tabs and the editor buffer on a debounce into a per-session folder keyed by pid and process start time (so a reused pid is not mistaken for a live session), written with `services/atomicWrite.ts`, removed on a clean close, and treated as orphaned when its process is gone. A mesh recipe restores through the provider's existing `backupCustomDocument` format, opened over the original file; a source that changed since the checkpoint is reported rather than replayed blindly. CAD tabs need nothing: their sidecars already autosave. *Chat parity: none* (session recovery); *docs:* `getting-started.md`'s session restore and quit sections.

### Tier 2 — Guided workflow completeness

3. **XDMF/HDF5 read-back: Kratos can write a correct index, the meshio++ reader cannot read it** (**S** app-side; the meshio++ half is unscoped — *needs upstream meshio++ work*). Live acceptance (`npm run workflows:outputs`) now passes the solver and discovery steps and fails only at read-back. On Kratos 10.4.2–10.4.4 (verified on 10.4.4, Linux, Python 3.12; the HDF5 wheel also needs the MPICH-ABI `libmpi.so.12`, e.g. the `mpich` wheel's `lib/` on `LD_LIBRARY_PATH`) `single_mesh_xdmf_output_process` has two defects: its XDMF step ignores `mock_hdf5_file_io` and opens the mesh file for real in `exclusive` mode (`OpenHDF5File.__enter__`), and `TimeLabel()` rewrites `e-` to `e*`, so a file stem ending in `e` (`Structure-0.1250.h5`) loses its time label and the time axis collapses. Defaults therefore fail with `Failed to open file: Structure.h5`. Settings that avoid both — `file_settings` `{file_name: "<model_part_name>_results-<time>", file_access_mode: "read_write"}` plus `HDF5_USE_FILE_LOCKING=FALSE` — write a correct index (nine distinct times, `DISPLACEMENT`, nine `.h5` companions) and KKSS discovery lists the entrypoint and every companion. The remaining blocker is the read itself: `@meshioplusplus/wasm` 16.31.0 and 16.32.0 reject that index with `XDMF: temporal collection carries no mesh grid`, even with the conditions grid removed and the spatial collection flattened, so `mesh__mesh_info` and `mesh__case_evaluate_quantity` fail. Close this after meshio++ reads Kratos's multi-file temporal layout (one `.h5` per step, mesh duplicated under `/ModelData`, a `Time` on every grid) and both submodules lock that release; then strengthen the harness's XDMF quantity check against the structural baseline and confirm revision checks on the companions. *Chat parity: none* (acceptance).

4. **Live MPI verification, partitioning fidelity and multi-node ranks** (**M**, remaining). The KKSS-side runner has landed: `workflows/mpiRunner.ts` launches a solve frozen with `kratos.mpiRanks` under `mpirun`/`mpiexec`/`srun` on this machine or the ssh host, owns the receipt through `mpiRunScript` (per-rank pid markers, `effectiveRanks`), reads *uncertain* for a short or partially-dead rank set, downloads checksum-verified outputs, and `EnvironmentReport.mpi` is now a probed boolean. It is exercised end to end through the real `WorkflowService`/queue with stand-in launchers, including a killed rank. What remains needs a machine with an MPI-enabled Kratos build (`KratosMultiphysics.mpi`, Trilinos, Metis): (a) run a published tutorial case on 2 and 4 ranks and compare against the threaded baseline — the `ProjectParameters` rewrite (`problem_data.parallel_type: "MPI"`) is only fixture-verified, and per-problemtype solver adapters (Trilinos linear solvers, distributed output processes) may need generator support on the mesh submodule's `kkss.dev` branch (now scoped there as mesh roadmap item 32, *MPI/Trilinos and CoSimIO generator variants*); (b) record a real partially-dead rank set (kill one rank of a live job); (c) multi-node launches, which the pid-based liveness check cannot cover; (d) MPI for CAD/mesh preparation tasks (none is parallel today). *Chat parity: shipped* (system prompt sentence; `kratos.mpiRanks` is a Settings row).

### Tier 3 — Model consistency across modes

*Admission: keeps geometry, mesh, case, runs and results coherent when one of them changes or is swept, building on the shipped revision-bound study store rather than a second dependency model. Items marked *needs upstream* name the submodule half.* *Chat parity:* same rule as Tier 2 — new or changed `app__*` tools need their schema, workflow prompt and `toolPolicy.ts` row in the same change.

5. **Region references survive geometry and mesh changes** (**M**; *needs upstream* CAD *Part rename and delete events for embedders* for the rename half). Problemtype boundary-condition and material assignments are keyed by SubModelPart path (`mesh/src/problemtype/caseFile.ts`), and so are saved monitors, quantity regions, view layers and a sweep's case paths — all of them, ultimately, a CAD Part name exported through the handoff. Renaming a Part, deleting one or re-exporting a changed geometry silently orphans those references; preflight later warns that a SubModelPart is missing, but by then the user has to reconstruct what it was. Add a carry-over report at the two moments that matter: before a CAD mesh export that will replace an attached study mesh (kept / renamed / lost / new regions, with every reference each one carries), and when a study's mesh is attached; offer to move a renamed region's assignments in one undoable case edit; and ask before deleting a Part that a case still references. This is ElmerStudio's dependency graph ("Used By", delete-in-use warnings, lost entities flagged) restricted to the one dependency KKSS actually breaks. Name matching alone cannot tell a rename from a delete plus an add, which is why the CAD half matters; until it lands, the report states which matches are by name only. *Chat parity:* a read-class `app__study_region_references` tool (rows in `toolPolicy.ts`), and the report's lost regions in the context suffix while the affected study is selected; *docs:* `getting-started.md`'s guided work section.

6. **Geometry-parameter sweeps** (**M**; builds on item 5; *optional upstream* CAD *Unit-aware document variables*). Today **Plan sweep** expands one case-setting dotted path (`workflows/service.ts`, `queue_parameter_sweep_preview`), so a geometry change — a longer plate, a larger fillet — is a manual loop of edit, export, attach, plan. CAD document variables are already settable headless and revision-guarded (`cad__set_variables`, `expectedRevision`). Add a sweep over one or more CAD variables whose plan, per row, copies the geometry source and its sidecars into the row's run directory (the user's own model is never edited), sets the variables there, exports the mesh with the study's frozen meshing options, regenerates the case and solves, all as ordinary queue tasks with the existing dependency order and CPU reservations. Each row freezes the variable values, the source revision and the resulting geometry revision in its provenance, and a row whose export loses a region (item 5) stops before solving. ElmerStudio's busbar sweep over the bar width is the reference workflow. *Chat parity:* the preview/enqueue tools gain a `geometryVariables` form (or a sibling `app__queue_geometry_sweep_preview`, read-class) with its policy row; the workflow prompt describes it; *docs:* guided work section and a tutorial step.

7. **Multi-parameter sweeps and quantity-versus-parameter review** (**S–M**). Sweeps take one path; variants take explicit rows. Add an *all combinations* expansion over several case paths (and, with item 6, CAD variables) and a *specified combinations* mode that pairs equal-length lists, both under the existing 50-row cap with the expansion shown before anything is persisted. In review and comparison, a saved quantity across a sweep becomes one table with the swept parameters as columns and a plot against a chosen parameter (mesh item 30 supplies the parameter-axis plot), preserving missing values as null. ElmerStudio's Global Evaluation over a parametric sweep is the model. *Chat parity:* the sweep preview schema gains the expansion modes; comparison results gain the per-parameter table.

8. **Warm-start sweep rows** (**M**; needs mesh item 29, *Restart and initial state from another run*, and a solver to verify). A stationary sweep whose mesh revision is unchanged between rows can start each row from the previous row's converged state, which ElmerStudio does through restart files ("reuse solution from previous step"). Add an opt-in `warmStart` to sweep plans: rows are chained in parameter order through the queue's existing dependency edges, a row records which run it started from, a mesh mismatch falls back to a cold start with a finding, and a failed predecessor never silently feeds the next row. *Chat parity:* the option on the sweep preview tool; review evidence names the predecessor run.

9. **Rebuild stale dependents** (**S**). Home already derives `ready`/`stale`/`missing` for geometry, mesh and case from recorded revisions (`workflows/project.ts`), and saved quantities on a changed result are shown as stale. Add one action that previews exactly what would re-run to make a selected study current — mesh export, case generation, solve, quantity re-evaluation — as an ordinary paused plan the user persists and starts, never an automatic rebuild. *Chat parity:* reuse the plan preview tools with a `staleOnly` option.

10. **Single-file project archive** (**S–M**). A study is relocatable inside its project folder, but sharing one means zipping a folder by hand and hoping every external reference came along. ## Non-goals / known constraints

- **Keeping app-specific submodule patches uncommitted or on a release branch** — shared workflow contracts can require upstream changes; commit those on the designated integration branches and move the parent gitlinks only to their committed revisions.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature. Narrower version: item 15, a study panel that navigates between the two viewers without merging them.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image is a separate tag of a separate distribution, and the installer stays lean. Narrower version: item 24, a user-initiated, app-managed Kratos runtime downloaded on request.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image), the authenticated web front end and a reference per-user orchestrator so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 21 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one, and item 25 is the bundle.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once. Narrower version: item 16 reaches a 3D mouse through Electron's WebHID, which needs no native module.
- **Model-enabled extensions** — the assistant may draft a skill, template or hook for the user to review and save, but it never trusts a folder, enables a server or turns a hook on. A hook runs before every approval, and a tool result that could switch one on would let the model approve its own calls. Enabling is a user action in the manager.
- **Vendor CLI extensions on the subscription runtimes** — the Claude Code and Codex plugin, hook, skill and MCP systems stay off (`settingSources: []`, `plugins: []`, `strictMcpConfig`, `CODEX_RESTRICTIONS`). Each would be a second gate the approval flow cannot see, so KKSS definitions reach those runtimes only through `executeTool`.
- **Alternative solver backends** — ElmerStudio runs selected models through OpenFOAM or NASTRAN-95 and refuses the rest with a reason; KKSS generates and verifies Kratos cases only, and its review, convergence and output-discovery contracts are Kratos-specific. A second solver would be a second copy of every one of them. What already exists instead: the mesh writers export to the other solvers' mesh formats, and the queue can run any command a user's own case script starts, without KKSS claiming its results. Revisit only for a concrete solver whose case and result contracts can be verified as strictly as the Kratos ones.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **5 → 6.** A geometry sweep re-exports the mesh per row, so it must stop on a lost region instead of solving a case whose boundary conditions silently fell away.
- **7 → 8, and mesh item 29 → 8.** Warm starts chain sweep rows, so the row expansion has to exist first, and the restart half lives in the mesh generators.
- **3 → 11.** Remote solves only become reviewable if result discovery has live acceptance for generated-case output settings rather than assuming a local `vtk_output/`.
- **21 → 27.** The remaining sharing and resize validation must be settled before the container and hardware acceptance checks can close.
