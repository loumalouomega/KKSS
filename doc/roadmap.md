# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two upstream VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* behind a fake `vscode` module — with scoped workflow-contract changes committed on their integration branches, OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over four MCP servers (CAD, mesh, Kratos and a pinned PDF reader) plus any the user adds, whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running, and optionally after the user's own lifecycle hooks have had their say — and whose image results are shown in the sidebar, a composer that attaches images and PDFs (stored with the conversation, refused up front where a provider cannot take them), a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 4" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** A change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for MCP contracts, `application-downstream` for extension code), is committed there, and is integrated here through its gitlink — never as an uncommitted patch or on the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- **Cite an item by name from outside this file; use its number only inside it.** Numbers move every time an item closes, and by 2026-11-10 some thirty comments in `app/`, `tools/`, `test/` and the workflows cited numbers that had since been reassigned. They were rewritten to name the feature, which is also what CAD-Preview's roadmap requires of its own citations. Mesh item numbers are stable (that file never renumbers), so "mesh item 29" stays a valid reference; CAD items are cited by title.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

### Tier 9 — Robustness and maintainability

*Admission: nothing a user asked for by name, and everything that decides whether the app survives a large model, a driver reset or its own growth. Items here are measured, not judged: each states the number or the test that closes it.*

43. **Graphics context loss and a large-model guard** (**S–M**; the viewer halves *need upstream* CAD *WebGL context-loss recovery* and the mesh equivalent under its item 2). And nothing warns before a file that will not fit is opened: the only size-aware path is mesh's header summary above 250 MB. ## Non-goals / known constraints

- **Keeping app-specific submodule patches uncommitted or on a release branch** — shared workflow contracts can require upstream changes; commit those on the designated integration branches and move the parent gitlinks only to their committed revisions.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget. Narrower version, queued: the command palette (item 20) finds and runs a viewer's own commands from one search box; it adds no menu entry and no second copy of a command, so the two surfaces this entry warns about do not arise. The one deliberate exception is Undo and Redo (item 1), which every platform expects in the Edit menu.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature. Narrower versions: the study panel (shipped), which navigates between the two viewers without merging them, and the side-by-side view (item 22) with a camera linked across modes (item 27), which shows a geometry and its results together while each stays in its own viewer and its own document.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image is a separate tag of a separate distribution, and the installer stays lean. Narrower version, shipped: **Install Kratos solver…**, a user-initiated, app-managed Kratos runtime downloaded on request. Re-read 2026-11-10 and kept: Pyodide for Python problemtypes (item 46(h)) is a problemtype loader a few megabytes in size, not a solver runtime, and is staged or not on its own measured cost.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image), the authenticated web front end and a reference per-user orchestrator so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 50 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one, Export Diagnostics is the bundle, and local crash dumps that are never uploaded (shipped) are the next part of it.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once. Narrower version: item 38 reaches a 3D mouse through Electron's WebHID, which needs no native module.
- **Model-enabled extensions** — the assistant may draft a skill, template or hook for the user to review and save, but it never trusts a folder, enables a server or turns a hook on. A hook runs before every approval, and a tool result that could switch one on would let the model approve its own calls. Enabling is a user action in the manager. Re-read 2026-11-10 and kept: the view-driving tools (item 41) change presentation only and pass the same gate, so they do not weaken this.
- **Vendor CLI extensions on the subscription runtimes** — the Claude Code and Codex plugin, hook, skill and MCP systems stay off (`settingSources: []`, `plugins: []`, `strictMcpConfig`, `CODEX_RESTRICTIONS`). Each would be a second gate the approval flow cannot see, so KKSS definitions reach those runtimes only through `executeTool`.
- **Alternative solver backends** — ElmerStudio runs selected models through OpenFOAM or NASTRAN-95 and refuses the rest with a reason; KKSS generates and verifies Kratos cases only, and its review, convergence and output-discovery contracts are Kratos-specific. A second solver would be a second copy of every one of them. What already exists instead: the mesh writers export to the other solvers' mesh formats, and the queue can run any command a user's own case script starts, without KKSS claiming its results. Revisit only for a concrete solver whose case and result contracts can be verified as strictly as the Kratos ones. Re-read 2026-11-10 and kept: every guided-workflow item added that day (continuing a run, adaptive refinement, the report builder, the Runs surface) leans on those contracts, so the cost of a second backend rose rather than fell. What did move upstream is breadth inside Kratos: contact, thermo-mechanical, DEM and MPM problemtypes are queued in the mesh roadmap (items 55, 68 and 69).
