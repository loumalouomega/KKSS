# Roadmap

Candidate work for future KKSS releases, prioritized by value versus effort given what the app already ships: two unmodified VS Code extensions running side by side — one *ported* (`cadHost.ts`), one *shimmed* verbatim behind a fake `vscode` module — with OCCT and Gmsh in a compute worker, MMG and meshio++ in the mesh submodule's own workers, a forked Flowgraph server, custom `kkss://` and `kkss-file://` schemes standing in for VS Code's webview plumbing, five screens over stacked `WebContentsView`s (home, the two mode screens — each holding any number of open documents as tabs — the text editor, plus a terminal panel and shared Chat/Jobs sidebar), an LLM agent loop over three MCP servers whose write-shaped tool calls are approved in the transcript before they run — optionally after being validated there without running — and whose image results are shown in the sidebar, a per-conversation token and cost readout, request-side compaction that keeps a long conversation inside the model's context window, an optional HTTP meta MCP server that re-exposes the same toolset, a cloud staging layer that opens Drive/Dropbox/OneDrive documents as ordinary local files, and a streamed-desktop Docker image. Many items below are cheap precisely because that infrastructure exists; a few are expensive precisely because of where its boundaries fall.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has the verified implementation details and non-negotiable invariants for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **An empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Every item states its chat-parity obligation.** `CLAUDE.md`'s "Keep chat features in sync" rule requires a new app capability to reach the assistant in the *same* change: the capability description in `app/main/services/chat/chatService.ts`'s system prompt, the server wiring in `app/main/services/chat/mcpManager.ts` if a new tool source is involved, the **Settings ▸ LLM Assistant** menu if it's configurable, and `ChatDeps.currentFiles()` / the context suffix if it's new context rather than a new ability (the system prompt stays byte-stable for prompt caching). Items whose surface the assistant genuinely cannot reach — window chrome, packaging, CI — say so explicitly, so the estimate includes the wiring rather than discovering it late.
- **Every item also carries a doc-parity cost.** `doc/`, `README.md` and `CLAUDE.md` move with the change, not after it; anything that alters the shell toolbar, the generated webview pages, or visible viewer behavior also means re-running `npm run docs:screenshots` (the PNGs are generated from the live app, never hand-captured).
- **Items marked *needs upstream submodule work* cannot land in this repo alone.** The zero-modification invariant means a change inside `cad/` or `mesh/` goes to that submodule's own branch (`kkss.dev` for the MCP servers, `application-downstream` for extension code) plus a gitlink bump here — never a local patch, and never the submodule's default branch. No such item may be *estimated* until the upstream half is scoped; each one names what it needs.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or strands a session rather than merely lacking a feature. Those belong in the top tier regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

## Non-goals / known constraints

- **Patching `cad/` or `mesh/` to make an app-level feature easier** — the zero-modification invariant is architectural, not a missing convenience. A genuinely unavoidable change goes to a dedicated branch in that submodule with the gitlink pointed at it, never to the submodule's default branch and never as a local edit.
- **Duplicating viewer actions in the native menu** — the menu bar holds app-level items only. Quality metrics, field visualization, find-entity and the rest live in the submodules' own toolbars; mirroring them would create two surfaces to keep in sync and one to forget.
- **Merging the two modes into one viewer or one document** — the asymmetric reuse (a 1:1 *port* for CAD because its provider imports OCCT directly, a verbatim *shim* for mesh) and two independent WebGL renderers mean this is a rewrite of the thing that makes the app cheap to maintain, not a feature.
- **A dirty-state prompt when closing a tab** — cad and mesh have no app-level "unsaved changes" concept; their sidecars autosave on a debounce, so closing a tab is a plain dispose, exactly like replacing a tab's document has always been. Adding a prompt would mean inventing a document-dirty model the submodules don't have.
- **Bundling Kratos or a Python runtime in the installer** — the package is already large (OCCT alone is ~63 MB of WASM, and `asar: false` means it ships unpacked); `uvx` sources the Kratos server on demand. The app-local uv bootstrap improves that path rather than replacing it. The `-kratos` image is a separate tag of a separate distribution, and the installer stays lean.
- **Operating a hosted KKSS service** — the repo ships the unit of deployment (the image), the authenticated web front end and a reference per-user orchestrator so that *someone else* can run one. User accounts beyond what an OIDC provider supplies, billing, quotas, backups of user volumes and an SLA are the operator's concern, not this project's; the single-container image stays the default, and item 5 keeps its one-session scope explicit rather than implied.
- **Hand-editing generated artifacts** — `out/renderer/*/index.html`, `app/renderer/shell/shellIcons.ts`, the doc screenshots and the icon SVG/PNGs are all pipeline output. Edit the source and re-run the pipeline.
- **Telemetry or usage analytics** — not planned, recorded here so it isn't re-proposed. The chat sidebar's token and cost readout is not an exception to this: it is computed in the main process from what the provider returned, shown only to the user whose key paid for it, and transmitted nowhere. Crash *diagnostics* the user can read and send by hand are a different thing and are not excluded; the renderer-crash toasts are the seed of one.
- **A second native module** — node-pty is deliberately the only one, and the only `node_modules` entry that ships. It is N-API, so it needs no electron-rebuild; anything requiring a rebuild step would change the release matrix for every platform at once.

## Dependencies

A few items must land in order, and getting it wrong means rework:

- **2 → 3.** The chat-driven tutorial reuses the manual one's worked example and pipeline description; writing it first means describing the same pipeline twice.
- **5 → 6.** The remaining sharing and resize validation must be settled before the container and hardware acceptance checks can close.
- **Simulation handoff + case/run contracts → study navigator → run review.** Land the CAD and mesh contracts upstream first; the navigator consumes them, and the review adds convergence/provenance when those capabilities become available. Environment checks can ship independently.
- **Document-scoped CAD jobs + isolated mesh runs → dependency-aware queue → parameter variants.** The queue consumes existing runner identities; study variants reuse the queue and the mesh result-comparison/quantity tools.
